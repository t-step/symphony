# Feature Specification: Bindle-Backed Work Tracking Through a Narrow Schedulable Projection

**Feature Branch**: `002-bindle-integration` (Spec Kit feature identifier only; per the fork's workflow — see `001-local-tracker-multi-agent` — no separate git branch is created for this feature; work stays on `development`)

**Created**: 2026-08-27

**Status**: Draft (corrected 2026-08-27 — see Correction Note below)

**Correction Note (2026-08-27)**: FR-013 and the related User Story 5 language were corrected — narrowly, without reopening this specification's architecture — to distinguish Bindle's `type = 'task'` execution-completion fact (`done`, agent-triggerable without human review) from `type = 'milestone'` human acceptance (`accepted`, never inferred from readiness). The prior wording's "semantic completion... MUST remain human-resolved" was overbroad enough to read as forbidding an agent from ever requesting its own bound task's ordinary `done` transition, which FR-009's existing agent-invoked tracker-write boundary already generically authorizes and Bindle's own model does not gate on human review. See spec.md's Assumptions for the grounding evidence and `research.md`'s new entry for the full rationale.

**Input**: User description: "Rework the current Symphony/Bindle integration design around the architecture we have now settled on. Bindle owns durable implementation state (slices, dependencies/blocking, claims, execution state, evidence, reconciliation state, other coordination metadata). Symphony must not own or reconstruct that model. Bindle exposes a deliberately narrow schedulable projection; Symphony consumes that projection through its existing tracker abstraction and produces its existing Tracker.Issue shape, unchanged. Symphony's scheduler/orchestrator must not need to understand Bindle's richer state. Symphony should primarily see top-level schedulable implementation units; blocked/nested/evidence-only/reconciliation-only items stay in Bindle and must not become assignable Symphony work. `dispatchable` (or equivalent) is an upstream fact from the projection, never recomputed by Symphony. Bindle mechanically verifies objective evidence; humans resolve semantic completion/correctness — this must not become a general-purpose workflow engine. The current SQLite-backed `Local.Store`/`Local.Adapter` (feature 001) is Symphony's own standalone local tracker, not the future canonical Bindle store, and must not be documented as the growth path for a richer Bindle model. Prefer the smallest architectural change; avoid shared mutable database ownership, JSON sync layers, Git-backed coordination state, hosted control planes, or unneeded new infrastructure."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build the Bindle-backed tracker as an ordinary Tracker adapter, not a scheduler change (Priority: P1)

An engineer implementing Symphony's future Bindle-backed tracker needs an unambiguous, narrow contract to build against: what Bindle must expose, what shape Symphony consumes, and — critically — confirmation that no *Bindle-specific* knowledge needs to leak into orchestrator, dispatcher, agent-runner, or workflow-store code to support it. Without this, the natural failure mode is scope creep: richer Bindle concepts (claims, evidence, milestones, dependency graphs) leaking into Symphony's scheduling core because no boundary was specified in advance.

**Why this priority**: This is the foundational architectural decision the whole feature exists to fix. Every other requirement in this spec depends on establishing that the seam is "another Tracker adapter," not a new subsystem.

**Independent Test**: Confirm, by inspection of `SymphonyElixir.Tracker`'s existing behaviour (`fetch_issues_by_states/1`, `fetch_issues_by_ids/1`, `agent_tool_specs/0`, `execute_agent_tool/3`, `secret_environment_names/1`, `validate_config/1`), one new narrow, optional, adapter-agnostic acquisition/release callback pair (FR-015), and `SymphonyElixir.Tracker.Issue`'s existing struct shape, that a Bindle-backed adapter can be described entirely in terms of those callbacks and that struct, with no Bindle-specific concept (claims, evidence, milestones, dependency graphs) appearing anywhere in orchestrator/dispatcher/agent-runner/workflow-store code.

**Acceptance Scenarios**:

1. **Given** this specification and Symphony's existing `Tracker` behaviour plus the one new optional acquisition/release callback pair (FR-015), **When** a future implementer designs the Bindle-backed adapter, **Then** they can express every requirement below using only the six existing `Tracker` callbacks, the new optional callback pair, and the existing `Tracker.Issue` fields — with no Bindle-specific vocabulary (claim, evidence, milestone, dependency graph) required anywhere in orchestrator-facing code, even though the optional callback pair itself is a genuine, load-bearing addition to the `Tracker` behaviour, not zero orchestrator-facing change.
2. **Given** a running Symphony deployment configured against a Bindle-backed tracker, **When** the orchestrator polls, dispatches, retries, or reconciles work, **Then** it applies exactly the same scheduling logic (dispatch order, concurrency limits, retry/backoff, reconciliation) it applies to any other tracker, calling the optional acquisition/release callbacks generically at points it already tracks claim/release state today, with no Bindle-specific branch anywhere in orchestrator/dispatcher/agent-runner/workflow-store code.

### User Story 2 - Perform real dispatch-time arbitration, not just trust a projection snapshot (Priority: P1)

An operator running Symphony against a Bindle-backed tracker needs confidence that when Bindle is the durable coordination authority for a work item, Symphony never treats a worker as having acquired that item without Bindle's own durable arbitration agreeing — even though the projection's `dispatchable` fact (User Story 3) is exactly the upstream signal Symphony uses to decide what to *attempt* to dispatch. A precomputed admission fact in a periodically-refreshed projection is necessarily a snapshot: it can be stale by the time Symphony actually acts on it, whether because of ordinary refresh latency, a second poll cycle racing the first, or (in a future multi-instance deployment) a second Symphony process reading the same projection concurrently.

**Why this priority**: Without this, `dispatchable: true` in the projection would be silently treated as a durable acquisition guarantee it was never designed to be, and two workers could be dispatched against the same Bindle work item — precisely the kind of derived-eligibility bug FR-003 already forbids for the read side, now addressed on the write/acquire side.

**Independent Test**: Confirm that, for a tracker capable of durable server-side claim arbitration, Symphony's orchestrator performs a real acquisition call against that authority immediately before treating any candidate issue as dispatched — never relying on the projection's admission fact alone as proof of acquisition — and that this call is expressed as one narrow, optional, adapter-agnostic `Tracker` behaviour seam that is a complete no-op for every adapter that does not need it.

**Acceptance Scenarios**:

1. **Given** a Bindle work item whose projection record currently reads `dispatchable: true`, **When** Symphony's orchestrator is about to dispatch it, **Then** the orchestrator first calls the tracker's optional acquisition callback (FR-015) and only proceeds to dispatch on a successful result; on any other result it skips dispatching that item in the current cycle, exactly as it already does today when a candidate fails `candidate_issue?`.
2. **Given** two concurrent attempts to acquire the same Bindle work item (whether two poll cycles or, in a future multi-instance deployment, two Symphony processes), **When** both call the acquisition callback, **Then** Bindle's own durable, atomically-arbitrated claim mechanism guarantees exactly one succeeds, and the other's failure is treated as "not currently available," never as an error requiring a crash or an alert.
3. **Given** a dispatched Bindle work item reaching any of Symphony's existing claim-release points (retry-exhausted, terminal-state transition, routed-away, or missing-issue detection), **When** that release point fires, **Then** the orchestrator calls the tracker's optional release callback (FR-015) at that same point, symmetrically with today's in-memory claim release — and does **not** call it merely because a retry is being scheduled, since the same workspace/branch is intentionally reused across retry backoff.
4. **Given** a tracker adapter that does not implement the optional acquisition/release callbacks (every adapter existing today — local, GitHub, GitLab, Jira, Linear, Asana), **When** the orchestrator dispatches or releases an issue from that tracker, **Then** its behavior is unchanged from today, byte-for-byte — the callback pair is a complete no-op for it.
5. **Given** the callback pair's crash-recovery behavior, **When** this specification is used to plan the eventual Bindle-backed adapter implementation, **Then** that planning stage MUST treat "a Symphony process crashes after a successful acquisition but before the corresponding work is fully underway" as a genuinely open design question this specification does not resolve (see FR-015) — not as an already-solved edge case.
6. **Given** a Bindle work item Symphony has already successfully acquired and is currently executing, **When** a subsequent poll's projection record for that same item now reads `dispatchable: false` — the expected, ordinary result of Bindle reporting a claimed item as unavailable to other acquirers — while the item's state remains active, **Then** Symphony's reconciliation MUST NOT terminate the running agent or release the held claim on that basis alone (FR-017); only a terminal-state transition, the item leaving the active-state set, or the item disappearing from the tracker's visible set continues to do so, exactly as before this specification.

### User Story 3 - See only independently schedulable work, never Bindle's internal bookkeeping (Priority: P1)

An operator running Symphony against Bindle-managed work wants Symphony's dispatch queue to contain only implementation units that are actually ready to hand to a coding agent right now — not every row in Bindle's ledger. Blocked work, sub-items of a larger slice, evidence records, and reconciliation-only bookkeeping entries are real and useful inside Bindle, but none of them are things a coding-agent session should ever be dispatched to work on directly.

**Why this priority**: This is the concrete mechanism that keeps Symphony's scheduler ignorant of Bindle's richer model. Get this wrong and Symphony either dispatches work it shouldn't (nested/blocked items) or under-dispatches because eligibility logic was reimplemented incorrectly on the Symphony side.

**Independent Test**: Given a Bindle ledger containing a mix of top-level schedulable units, blocked units, nested sub-items, evidence-only records, and reconciliation-only records, confirm that only the top-level schedulable units appear in the Bindle-facing projection Symphony reads, and that each one carries a pre-computed admission fact (equivalent to today's `dispatchable`) that Symphony consumes verbatim rather than deriving from blocking/nesting/evidence state.

**Acceptance Scenarios**:

1. **Given** a Bindle work item that is blocked by an unresolved dependency, **When** Symphony's tracker adapter reads the projection, **Then** that item either does not appear in the projection at all, or appears with its admission fact set to not-dispatchable — in neither case does Symphony consult Bindle's dependency/blocking data directly to make that determination itself.
2. **Given** a Bindle work item that is nested under a larger slice, evidence-only, or reconciliation-only, **When** Symphony's tracker adapter reads the projection, **Then** that item never appears in the projection, regardless of any other state it holds in Bindle.
3. **Given** a top-level Bindle work item that becomes blocked between two polls, **When** Symphony polls again, **Then** the projection reflects the new admission state (item removed, or its admission fact flips) without Symphony having recomputed eligibility from richer Bindle state.

### User Story 4 - Choose standalone local tracking or Bindle-backed tracking without ambiguity (Priority: P2)

An operator configuring a Symphony deployment wants to pick exactly one work-tracking source — Symphony's own standalone local tracker, a Bindle-backed tracker, or a hosted tracker — and have no doubt about which one is active, with no shared state or silent substitution between the standalone local tracker and a Bindle-backed tracker.

**Why this priority**: Directly prevents the specific confusion this feature exists to correct: conflating Symphony's own standalone local tracker with a future Bindle-backed store merely because of a shared persistence detail — a risk independent of whatever storage format the standalone local tracker happens to use at any given time (currently JSON-file-backed; see `001-local-tracker-multi-agent`).

**Independent Test**: Confirm that Symphony's tracker-selection configuration treats "standalone local tracker" and "Bindle-backed tracker" as two distinct, mutually exclusive choices within the existing single-active-work-tracking-source model, and that no code path or documentation implies one is a subset, precursor, or storage layer of the other.

**Acceptance Scenarios**:

1. **Given** a deployment configured to use Symphony's standalone local tracker, **When** an operator or future maintainer reads its documentation or source, **Then** nothing states or implies that its database, schema, or module is the location a future Bindle-backed tracker's data will live in or grow into.
2. **Given** a deployment, **When** it selects a work-tracking source, **Then** exactly one of {a hosted tracker, the standalone local tracker, a Bindle-backed tracker} is active, consistent with the existing single-active-source model (`001-local-tracker-multi-agent` FR-012) — a Bindle-backed tracker is one more alternative for that same single slot, not a second concurrently active source.

### User Story 5 - Keep mechanical evidence inside Bindle and semantic judgment with humans (Priority: P3)

A team wants Bindle to catch objective, mechanically-checkable gaps (a required file never changed, a check never ran, no commit exists, an expected artifact is missing, a dependency/state transition is internally inconsistent) without Symphony reimplementing any of that logic, while trusting that whether the *work itself* is actually correct or complete remains a human call, not something either system infers automatically.

**Why this priority**: Lower priority than the architectural boundary itself, but explicitly called out because the natural next mistake — once mechanical verification exists — is to keep expanding it until it quietly becomes a semantic-completion or general workflow engine.

**Independent Test**: Confirm this specification names concrete categories of mechanical evidence Bindle may check, states plainly that Symphony performs none of that checking itself, and states plainly that milestone acceptance is not automated by either system from passing evidence alone — while also confirming the specification distinguishes that from an agent's own explicit, narrow request to mark its bound *task* done (FR-013), which is not "automation" in the sense this story guards against.

**Acceptance Scenarios**:

1. **Given** a Bindle-managed work item whose mechanical evidence checks (file changes, expected tests/checks, commit existence, artifact production, dependency/state consistency) have not been satisfied, **When** Bindle evaluates it, **Then** Bindle — not Symphony — is the system that determines it is not yet ready, and Symphony's only visibility into that fact is through the item's ordinary state/admission fields in the projection.
2. **Given** a Bindle-managed milestone whose child tasks' mechanical evidence checks all pass (making it review-ready), **When** a human has not yet explicitly accepted it, **Then** neither Bindle nor Symphony automatically transitions that milestone to `accepted` on the human's behalf — review-readiness never cascades into acceptance, either automatically or via anything this specification authorizes.
3. **Given**, separately, a Bindle-managed *task* a coding-agent session is bound to, **When** that agent's own execution work on the task is finished, **Then** the agent MAY explicitly request that task's own `done` transition through Symphony's existing agent-invoked, host-executed tracker-write boundary (FR-009/FR-013) — a narrow, mechanical, agent-triggerable execution-completion fact Bindle's own model does not require or trigger human review for — and this is not the "automated semantic completion" this story and FR-013 forbid, since it is an explicit, scoped, agent-initiated report of the agent's own finished work, not an inference either system draws on the agent's behalf from passing evidence checks.

### Edge Cases

- What happens when the Bindle-facing projection is temporarily unreachable during a poll or reconciliation pass? Symphony MUST treat this the same way it already tolerates any other tracker/source outage — skip the affected poll tick or reconciliation pass, retry on the next one, and leave already-running work-item attempts undisturbed (mirrors `001-local-tracker-multi-agent` FR-008.3) — not as an individual work-item attempt failure.
- What happens when a Bindle-backed tracker that has previously been operating becomes permanently misconfigured or unreachable (as opposed to a transient outage)? Symphony MUST surface this as an operator-visible failure of the work-tracking source itself, to the extent the Bindle-facing projection interface can supply that distinction — see FR-007 for the honest limits of what this spec can guarantee here without a concrete projection interface already in hand.
- What happens if an operator has both a previously-established standalone local tracker database and a Bindle-backed tracker configured for the same deployment over time? The two are entirely independent stores with no automatic migration, synchronization, or data sharing between them; switching a deployment's `tracker.kind` selection is an explicit operator action with no implied carryover of state from one to the other.
- What happens when a Bindle work item's admission fact and its blocking/dependency state seem to disagree (for example, a projection bug marks something dispatchable while it is still blocked upstream in Bindle)? This is a Bindle-side projection defect; Symphony has no independent way to detect or correct it, since Symphony is specified to trust the projection's admission fact as an upstream fact by design (FR-003) rather than cross-checking it against blocking state it is not given.
- What happens to an in-flight coding-agent run for a Bindle-managed item when a subsequent poll's projection record for that same item now reads `dispatchable: false` while its `status`/state remains active — including, and especially, the expected and ordinary case where this is simply Bindle correctly reporting the item as claimed after Symphony's own successful acquisition (FR-015)? Symphony's admission-vs-continuation invariant (FR-017) governs this precisely: `dispatchable` gates only whether Symphony *begins* a new dispatch; it MUST NOT, by itself, be treated as a reason to terminate an execution or release a claim Symphony already holds. Reconciliation for an already-running or already-blocked item continues to terminate/release on terminal-state transition, on the item leaving the active-state set, or on the item disappearing from the tracker's visible set — exactly as before — but MUST NOT do so merely because `dispatchable` flips to `false` on its own. Without this correction, the ordinary claim-then-dispatch sequence FR-015 requires would cause Symphony to terminate its own just-started execution on the very next poll (verified directly against `SymphonyElixir.Orchestrator.reconcile_issue_state/4`/`reconcile_blocked_issue_state/4` and `SymphonyElixir.AgentRunner.continue_with_issue?/2`, all three of which currently reuse the same `dispatchable`-gated admission predicate for this continuation decision — see FR-017 and research.md R11). This is a correction to Symphony's own generic reconciliation semantics, required for every tracker, not a Bindle-specific carve-out or new mid-run cancellation behavior beyond what FR-017 defines.
- What happens if a Symphony process crashes after successfully acquiring a Bindle work item (FR-015) but before that work item's coding-agent run is fully underway? Bindle's durable claim has no expiry of its own — this specification does NOT claim this is already solved. It is a genuinely open design question the eventual Bindle-backed-adapter implementation feature MUST resolve (most plausibly via startup-time reconciliation that releases this Symphony instance's own stale claims), not an edge case this specification can wave away by assuming the callback pair alone is sufficient.
- What happens when the published projection artifact's schema no longer matches what Symphony's adapter expects (a Bindle-side upgrade changes or removes a column)? Symphony MUST fail loud and treat this the same as any other unreachable/misconfigured tracker source (FR-007/FR-008), never silently misread a renamed or reordered column — see FR-002's schema-version requirement.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Symphony MUST be able to consume Bindle-managed work exclusively through its existing `SymphonyElixir.Tracker` adapter boundary and produce the existing `SymphonyElixir.Tracker.Issue` struct, unchanged in shape, exactly as every other adapter (GitHub, GitLab, Jira, Linear, Asana, the standalone local tracker) already does.
- **FR-002**: Bindle MUST deliberately publish a read-only projection artifact for Symphony to read — a physically separate SQLite database file from Bindle's own canonical ledger file, containing only a purpose-built view/table scoped to the fields in this specification's Key Entities section, never Bindle's canonical tables (`work_items`, `work_item_blocked_by`, `work_item_claims`, `work_item_evidence`) directly. This projection artifact MUST expose only top-level, independently schedulable implementation units — items that are blocked, nested under another unit, evidence-only, reconciliation-only, or otherwise not independently schedulable MUST NOT appear to Symphony as assignable work, either by being absent from the projection or by carrying a non-dispatchable admission fact per FR-003. The published artifact MUST carry a schema-version marker Symphony's adapter validates before treating it as a valid projection (protects against a misconfigured `tracker.provider.path` accidentally pointing at Bindle's canonical file, or a schema change happening silently underneath a running deployment); Symphony's adapter MUST query the projection by column name, never positionally. Physical separation of the artifact file prevents Symphony from ever reaching Bindle's canonical tables, but does not by itself make the artifact read-only to Symphony's own process; Symphony's adapter MUST additionally open the published artifact using SQLite's own read-only open mode (e.g. a read-only connection/URI such as `mode=ro`, not merely an adapter implementation that happens never to issue a write statement), and MUST NOT create, migrate, or repair the artifact file under any circumstance — publication and replacement of the artifact belong to Bindle alone.
- **FR-003**: Dispatch admission (a `dispatchable` boolean column on the published projection) for a Bindle-managed item MUST be supplied by the projection as a precomputed, upstream fact. Symphony MUST NOT derive, infer, or recompute dispatch eligibility from Bindle's richer state (dependency graphs, claims, evidence, reconciliation state) itself. This fact is a point-in-time snapshot and MAY be stale by the time Symphony actually attempts to dispatch — see FR-015 for why this does not mean Symphony second-guesses the fact itself, only that a separate, real-time acquisition step still happens at dispatch time.
- **FR-004**: Symphony's orchestrator, dispatcher, agent runner, and workflow store MUST NOT require any knowledge of Bindle's internal model — claims, evidence, reconciliation state, milestones, or dependency-graph internals — beyond what already exists on `Tracker.Issue` (state, labels, priority, `blocked_by` refs, `dispatchable`, and the other existing fields) plus the one narrow, optional, adapter-agnostic acquisition/release callback pair defined in FR-015. That callback pair is a genuine, load-bearing addition to the `Tracker` behaviour — this requirement is about Bindle-specific *vocabulary* never leaking into orchestrator-facing code, not about zero change to the `Tracker` behaviour itself.
- **FR-005**: A Symphony deployment MUST have at most one active work-tracking source at a time. A Bindle-backed tracker is one additional alternative within that existing single-active-source slot (`001-local-tracker-multi-agent` FR-012) — alongside a hosted tracker and Symphony's standalone local tracker — never a second, simultaneously active source.
- **FR-006**: Selecting a Bindle-backed tracker MUST be a distinct, explicit configuration choice from selecting Symphony's own standalone local tracker. An operator MUST NOT be able to configure one and unknowingly get the other, and neither selection MUST silently substitute for the other.
- **FR-007**: Symphony SHOULD distinguish, for a Bindle-backed tracker, between "not yet reachable/configured" and "previously operating, now failing," the same way `001-local-tracker-multi-agent` FR-013 requires for the standalone local tracker — to the extent the eventual Bindle-facing projection interface can supply that distinction. This specification does not assume a concrete projection interface already exists to guarantee it; the eventual implementation's planning stage MUST confirm what distinction the chosen interface can actually provide and MUST surface any gap explicitly rather than silently assume it is solved.
- **FR-008**: A transient failure to read the Bindle-facing projection during polling or reconciliation MUST be handled by Symphony's existing tracker/source failure handling — skip the affected poll tick or reconciliation pass, retry on the next one, leave already-running work-item attempts undisturbed — MUST NOT be treated as an individual work-item attempt failure.
- **FR-009**: Lifecycle-state mutations a coding-agent *session* performs against a Bindle-managed work item — i.e., a change to the item's semantic status or evidence, requested on the item's behalf as work progresses — MUST flow through Symphony's existing agent-invoked, host-executed tracker-write boundary (`agent_tool_specs/0` + `execute_agent_tool/3`) and MUST go through a Bindle-owned supported write operation, never a raw SQL mutation issued by Symphony's own process against any Bindle-owned database file (canonical or published). This feature MUST NOT add a new orchestrator-owned API for *this* category of write. See FR-015 for the one distinct, narrower category of orchestrator-owned write this specification does authorize.
- **FR-010**: Any tracker-write tool Symphony exposes against a Bindle-managed item MUST be scoped to the work item bound to the current coding-agent session, mirroring the existing standalone local tracker's `local_tracker_set_state` scope restriction — it MUST NOT be able to target an arbitrary Bindle work item.
- **FR-011**: This specification MUST NOT define, invent, or require any Bindle-internal capability beyond what is needed to define the Symphony-facing projection's contract (its membership rules, admission semantics, and failure surface) and the narrow acquisition/release contract in FR-015. Bindle's own internal ledger schema, dependency/claims/evidence/reconciliation engine, durable-storage mechanism, and the concrete publish mechanics (refresh cadence, atomic-rename implementation) of the projection artifact remain entirely out of scope for Symphony's specification and implementation.
- **FR-012**: Bindle's mechanical evidence verification (whether required files changed, whether expected tests/checks ran and passed, whether commits exist, whether artifacts were produced, whether dependency/state transitions are internally consistent) MUST remain entirely inside Bindle. Symphony MUST NOT reimplement, duplicate, or partially reimplement any of this verification.
- **FR-013**: Symphony MUST NOT infer semantic correctness or completeness for Bindle-managed work, and MUST NOT automatically mark any Bindle work item `done` or a milestone `accepted` merely because Bindle's own mechanical evidence checks pass — passing evidence never by itself authorizes a completion or acceptance decision. This MUST NOT be read as forbidding an agent working its own bound Bindle *task* from explicitly requesting that task's normal `done` transition: Bindle's own model (`type = 'task'` vs `type = 'milestone'`, verified directly against `specs/002-milestone-task-work-items/spec.md` and `docs/DECISIONS.md` D038) treats a task reaching `done` as a narrow, mechanical, agent-triggerable execution fact that does not require or trigger human review, distinct from *milestone acceptance* — the human semantic judgment that a grouped outcome is actually acceptable, recorded only by an explicit `review → accepted` transition (`accept_milestone()`) Bindle itself never infers from review-readiness alone. Any such agent-initiated task-`done` request MUST flow through Symphony's existing agent-invoked, host-executed tracker-write boundary (FR-009), MUST be scoped to the one task bound to the requesting session, and MUST use Bindle's own supported write operation (`bindle work done <id>`) — this is not a new capability beyond what FR-009 already generically authorizes for agent-initiated lifecycle-state mutations, only a clarification that this specific mutation is one instance of it. Milestone acceptance MUST remain resolved only within Bindle (or upstream of it) by a human; neither this specification nor any future implementation of it MUST introduce automated milestone-acceptance inference, whether from passing evidence, from a task's `done` state, or from any other mechanical signal.
- **FR-014**: Symphony's own standalone local tracker (`SymphonyElixir.Local.Store`/`SymphonyElixir.Local.Adapter`, `001-local-tracker-multi-agent`) and its documentation MUST NOT describe or imply that its storage, schema, or module is the location a future Bindle model will grow into, is shared with a future Bindle-backed tracker, or is otherwise the same system as one. **`development`'s current moduledoc already satisfies this** — verified directly by reading `elixir/lib/symphony_elixir/local/store.ex` during this specification's correction pass: it carries no such language to begin with (it was never introduced on this file's actual history), not a correction that was applied and landed here — no documentation change to this file is required for this feature to satisfy FR-014.
- **FR-015**: When the active tracker is a durable coordination authority capable of arbitrating concurrent acquisition of the same work item (such as a future Bindle-backed tracker), Symphony's `Tracker` behaviour MUST expose one narrow, OPTIONAL pair of callbacks — an acquisition callback and a release callback — that the orchestrator calls, when the active adapter implements them, at the two points it already tracks claim/release state today: immediately before treating a candidate issue as dispatched (acquisition), and at every existing point a claim is released today — retry-exhausted, terminal-state transition, routed-away, or missing-issue detection (release), but *not* merely because a retry is being scheduled, since the same workspace/branch is intentionally reused across retry backoff. For any adapter that does not implement these callbacks (every adapter existing as of this specification — local, GitHub, GitLab, Jira, Linear, Asana), this MUST be a complete no-op with zero behavior change. Symphony MUST NOT treat the projection's `dispatchable` fact (FR-003) alone as sufficient proof of acquisition when the active adapter implements this callback pair. This specification deliberately does NOT resolve two design questions it identifies as genuinely open, to be resolved by the eventual Bindle-backed-adapter implementation feature's own planning stage, not assumed solved here: (a) where in the dispatch sequence enough information (e.g., a computed workspace path) exists to satisfy Bindle's actual claim parameters, given the workspace is otherwise only materialized after a Task is already spawned; and (b) how a Symphony instance recovers a durable claim left stranded by its own crash between a successful acquisition and that work being fully underway, since Bindle's claims carry no expiry of their own. A stable owner identity for these calls is new state Symphony does not have today and must define, not something already available to reuse.
- **FR-016**: The acquisition/release calls in FR-015 are an orchestrator-owned write against the tracker, but MUST be treated as a distinct, narrower category from the agent-initiated lifecycle-mutation writes governed by FR-009: they MUST be scoped exclusively to calling a Bindle-owned supported claim/release operation, MUST NOT read or write any lifecycle-state field, and MUST NOT be satisfied by a raw SQL mutation against any Bindle-owned database file. FR-009's prohibition on a new orchestrator-owned tracker-write API applies to lifecycle-state writes specifically and does not prohibit this narrower, claim-scoped exception.
- **FR-017**: `dispatchable` (FR-003) MUST be treated by Symphony as a start/admission gate only — consulted when deciding whether to begin a *new* dispatch of an issue Symphony does not already have running or blocked state for — and MUST NOT, by itself, be treated as a continuation or preemption gate for an issue Symphony has already begun executing or already holds a block/claim entry for. Concretely: an issue's `dispatchable` fact flipping to `false` after Symphony has already begun dispatch — including, and especially, immediately after Symphony's own successful acquisition via FR-015, since a durable-claim-aware tracker naturally reports a just-claimed item as no-longer-dispatchable to *other* would-be acquirers, as expected, ordinary behavior rather than a fault — MUST NOT, on its own, cause Symphony to terminate the running agent or release the held block/claim for that issue, and MUST NOT cause a multi-turn agent run to end early. Symphony's existing terminal-state, non-active-state, and missing-from-tracker (id no longer visible in the tracker's fetched set) reconciliation checks are unaffected by this requirement and MUST continue to terminate/release exactly as they do today — this requirement narrows only the role `dispatchable` plays in reconciliation; it changes nothing about those other checks, and it introduces no Bindle-specific branch (it is a generic correction to how Symphony interprets `dispatchable` for every tracker). This is not a zero-impact change for every existing adapter — see research.md R11 for the per-adapter compatibility analysis and the two real, unresolved existing behaviors it identifies (Linear's assignee-reassignment continuation stop, confirmed load-bearing; Asana's `completed`-vs-section-name gap, confirmed structurally possible) that the eventual implementation feature MUST explicitly resolve — preserved through a distinct mechanism or explicitly, knowingly dropped — rather than silently assumed already covered.

### Key Entities

- **Bindle-Facing Schedulable Projection**: A physically separate, read-only SQLite database artifact Bindle deliberately publishes for Symphony — distinct from Bindle's own canonical ledger file, never a view living inside it. Each record corresponds 1:1 to a top-level, independently schedulable Bindle implementation unit and exposes exactly: `id` (stable identity), `identifier` (human-facing identifier — MAY reuse Bindle's own `id` if Bindle has no separate one), `title`, `description`, `status` (Bindle's own native status string, mapped verbatim onto `Tracker.Issue.state` with no synthesis), `dispatchable` (precomputed admission fact, FR-003), and `created_at` (needed so Symphony's existing dispatch-order sort does not collapse to alphabetical-by-identifier for every simultaneously-eligible Bindle item). Every other `Tracker.Issue` field (`native_ref`, `priority`, `branch_name`, `url`, `assignee_id`, `labels`, `blocked_by`, `updated_at`) is left at its existing struct default — none of them gate any dispatch/candidacy decision, and Bindle's own data model has no equivalent for most of them. The artifact MUST carry a schema-version marker Symphony validates at open time. It carries no claims, evidence, milestone, or dependency-graph detail. Its concrete publish mechanics (refresh cadence, atomic-rename implementation) are an implementation decision for the eventual Bindle-backed-tracker feature's planning stage; the artifact's physical shape (separate file, read-only, schema-versioned) is fixed by this specification. Symphony's adapter opens this artifact exclusively via SQLite's own read-only open mode and never creates, migrates, or repairs it (FR-002) — physical file separation alone is not sufficient to make the artifact read-only to Symphony's own process.
- **Bindle-Backed Tracker (Symphony-side)**: A future `SymphonyElixir.Tracker` adapter, structurally analogous to the existing `local`/`github`/`gitlab`/`jira`/`linear`/`asana` adapters, that reads only the Bindle-Facing Schedulable Projection, calls the optional acquisition/release callback pair (FR-015) to perform real-time dispatch arbitration, and writes only narrowly-scoped lifecycle mutations back through a Bindle-owned write path (FR-009). It owns no Bindle state of its own and reconstructs none of Bindle's richer model.
- **Tracker Acquisition/Release Seam** (new, FR-015): A narrow, optional pair of `SymphonyElixir.Tracker` behaviour callbacks the orchestrator calls, when the active adapter implements them, immediately before dispatch and at every existing claim-release point. Adapter-agnostic and generic in name and shape — no Bindle vocabulary (claim, worktree, branch) appears in the `Tracker` behaviour's public contract itself, even though a Bindle-backed adapter's own implementation of these callbacks is free to be as Bindle-specific as it needs internally. A complete no-op for every adapter that does not implement it.
- **Symphony Standalone Local Tracker** (existing, unchanged by this feature — see `001-local-tracker-multi-agent`): Symphony's own independent local work-tracking implementation — currently JSON-file-backed in `development` as of this specification's correction pass (`elixir/lib/symphony_elixir/local/store.ex`); a separate, independently-tracked conversion of this same module to SQLite exists on branch `local-tracker-sqlite` but is not part of `development` and not part of this feature. Explicitly a different system from a future Bindle-backed tracker, sharing no storage, schema, or growth path with it, regardless of which persistence mechanism either one uses at any given time — this feature's ownership boundary does not depend on, and must never be re-derived from, a shared storage format.
- **Bindle Durable Implementation Ledger** (owned entirely by Bindle, out of scope for Symphony's own specification/implementation): Slices/top-level work units, dependencies/blocking, claims, execution state, evidence, reconciliation state, and other coordination metadata. Referenced here only to establish the ownership boundary; its internal shape is not specified by this document.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A future implementer can build the Bindle-backed tracker as a single new `Tracker` adapter module, following the existing `local`/`github`/`gitlab`/`jira`/`linear`/`asana` package shape, registering it the same way `001-local-tracker-multi-agent` registered the standalone local tracker, plus implementing the one new optional acquisition/release callback pair (FR-015) — with zero Bindle-specific concept (claim, evidence, milestone, dependency graph) leaking into orchestrator, dispatcher, agent-runner, or workflow-store code.
- **SC-002**: In every scenario documented in this specification, no Bindle work item that is blocked, nested, evidence-only, or reconciliation-only appears to Symphony as schedulable or dispatchable work.
- **SC-003**: No source comment, moduledoc, or README section in this repository describes Symphony's standalone local tracker as the future home of a richer, externally-owned (Bindle) work model — verified already true for `elixir/lib/symphony_elixir/local/store.ex` as of this specification's rework (FR-014).
- **SC-004**: An operator can determine, from a deployment's own configuration, which one of {hosted tracker, standalone local tracker, Bindle-backed tracker} is active, with no configuration state shared between the standalone local tracker and a Bindle-backed tracker.
- **SC-005**: A team can run one Symphony deployment against Bindle-managed work and a separate deployment against a hosted tracker or the standalone local tracker without either deployment's tracker choice or data affecting the other, preserving the existing single-active-work-tracking-source invariant.
- **SC-006**: No two coding-agent sessions are ever dispatched concurrently against the same Bindle work item — verified by Bindle's own durable claim arbitration succeeding for exactly one of any two concurrent acquisition attempts (FR-015), not by Symphony's own bookkeeping alone.
- **SC-007**: Across every scenario this specification documents, an issue's `dispatchable` fact flipping to `false` after Symphony has already begun executing it or already holds a claim/block entry for it never, by itself, causes Symphony to terminate that execution or release that claim — verified against `SymphonyElixir.Orchestrator.reconcile_issue_state/4`, `reconcile_blocked_issue_state/4`, and `SymphonyElixir.AgentRunner.continue_with_issue?/2` (FR-017).

## Out of Scope / Non-Goals

- Designing or specifying Bindle's own internal schema, storage engine, dependency/claims/evidence model, or reconciliation logic — that belongs to Bindle's own project, not this repository's specification.
- Implementing the Bindle-backed `Tracker` adapter itself, or Bindle's own mechanism for publishing the projection artifact (refresh cadence, atomic-rename implementation, hosting/deployment of the publish job) — this specification fixes the projection's physical *shape* (a physically separate, read-only, schema-versioned SQLite artifact, FR-002) and its consumption contract, not Bindle's implementation of producing it, nor the Symphony-side adapter code itself.
- Implementing the new `Tracker` behaviour acquisition/release callback pair (FR-015) or the orchestrator wiring/crash-recovery reconciliation it requires — this specification establishes that this seam is required and fixes its narrow shape and semantics; building it is implementation work for a subsequent feature, not this specification.
- A second orchestration engine, workflow engine, or generic task-lifecycle framework inside Bindle or Symphony.
- Teaching Symphony to understand claims, evidence, reconciliation state, milestones, or dependency-graph internals for any purpose beyond consuming the narrow projection and the narrow acquisition/release seam this specification defines.
- Automated *inference* of semantic correctness, completeness, or milestone acceptance from mechanical evidence — this remains human-resolved by design (FR-013), not a gap to be closed by future automation. This does not exclude an agent's own explicit, scoped request to mark its bound Bindle *task* (not a milestone) done through the existing FR-009 tracker-write boundary — that is a distinct, narrower, already-authorized category of write FR-013 clarifies rather than a new automation this specification introduces.
- Any migration or synchronization mechanism between Symphony's standalone local tracker and a future Bindle-backed tracker; the two are independent, non-interacting stores, regardless of the standalone local tracker's own persistence mechanism at any point in time. A separate, independently-tracked conversion of Symphony's own standalone local tracker from JSON to SQLite exists on branch `local-tracker-sqlite`, has zero coupling to this feature, and is not part of `development` (see `plan.md` for the repository-hygiene history).
- Implementing FR-017's corrected reconciliation logic itself — splitting `Issue.routable?/2`'s admission role from a distinct continuation/routing check, and preserving today's real per-adapter continuation behaviors (research.md R11, e.g. Linear's assignee-reassignment stop) — this specification requires the correction and fixes its invariant; building it, for every tracker (not only a future Bindle-backed one), is implementation work for a subsequent feature.
- Shared mutable database ownership between Symphony and Bindle, a JSON synchronization layer, Git-backed coordination state, a hosted control plane, or any other new infrastructure dependency not demonstrably required by the requirements above.
- Rewriting or reopening `001-local-tracker-multi-agent`'s frozen specification, plan, or tasks.

## Assumptions

- Bindle is a separate system, developed and evolved outside this repository; this specification defines the Symphony-facing seam it must expose (the published projection artifact, FR-002/FR-003, and the acquisition/release contract, FR-015), not Bindle's own architecture.
- **The published, physically separate, read-only SQLite projection artifact this specification requires (FR-002) now exists in Bindle's codebase, built after this specification's own correction pass.** Re-verified directly against Bindle's actual implementation during a 2026-08-27 cross-repo reconciliation pass (`~/Developer/bindle`, HEAD `d70bc30`, `docs/DECISIONS.md` D039, `src/bindle/symphony_projection.py`'s `publish()`, `contracts/symphony-projection-v1.md`): the artifact is a physically separate, versioned (`PRAGMA user_version = 1`), read-only-by-contract SQLite file (`.bindle-work/symphony-projection.sqlite3`), distinct from Bindle's internal `ledger.sqlite3`, containing exactly one row per non-archived `type = 'task'` work item with a direct `status` string and a precomputed `dispatchable` boolean — matching this specification's Key Entities shape. This corrects the prior verification (checked against an earlier Bindle HEAD, `3dddedb`, before D039 landed) that found the artifact not yet built; this specification's forward requirement (FR-002) has since been satisfied on Bindle's side, though the Symphony-side adapter that reads it remains unbuilt (see "Out of Scope").
- **`dispatchable` currently carries no `parent_id`/nesting-based exclusion, because Bindle has no task-under-task nesting concept to exclude — FR-002's "nested under another unit" clause is correctly worded but presently vacuous.** Verified directly against Bindle's schema and D040 (`docs/DECISIONS.md`): a task's `parent_id` can only ever name a `type = 'milestone'` row (schema `CHECK`), never another task, and it records human-review attribution only (D038) — orthogonal to dispatch eligibility, which the published projection derives purely from `status`/claim/blocking state with no `parent_id` involvement at all. Bindle's own Spec Kit loader never sets `parent_id` on a loaded task in the first place. This means, as of this pass, every row Bindle's projection publishes already is a top-level, independently schedulable unit by construction (D038's `type = 'task'` filter plus D039's `dispatchable` derivation) — there is currently no "nested, non-schedulable child task" case in Bindle's model for FR-002's exclusion clause to need to filter out. That clause remains correctly specified as defense against a nesting concept Bindle could add in the future; it does not describe a gap in Bindle's current implementation, and no change to FR-002 or Bindle's model was made or is needed to close this ambiguity.
- The existing `SymphonyElixir.Tracker` behaviour and `Tracker.Issue` struct (confirmed against `SPEC.md` §11 and the current adapter implementations) are sufficient to represent a Bindle-managed top-level work item's *read* side without any new field. One narrow, optional callback pair (FR-015) is a confirmed, necessary addition to the behaviour itself for the *acquisition* side — this was verified by tracing Symphony's actual dispatch/claim code during this specification's rework, not assumed away.
- A future Bindle-backed adapter is added to Symphony's existing `Tracker.@adapters` map the same way `local` was added in `001-local-tracker-multi-agent`, and implements the FR-015 callback pair; no Bindle-specific vocabulary enters orchestrator-facing code as a result of that registration.
- The concrete `tracker.kind` value and configuration field names for a Bindle-backed tracker are left unspecified here and belong to the eventual implementation feature's planning stage, consistent with how `001-local-tracker-multi-agent` deferred its own lifecycle-write mechanism (its FR-003/FR-011) to planning.
- The projection's physical shape (a separate, read-only, schema-versioned SQLite artifact) is fixed by this specification (FR-002); its publish mechanics — refresh cadence, the atomic-rename implementation, where the publish job runs — remain a planning-stage decision for the eventual implementation feature.
- FR-014 is satisfied by `elixir/lib/symphony_elixir/local/store.ex`'s current moduledoc as it already stands on `development` — verified directly by reading the file during this specification's correction pass, not merely assumed. This is **not** a fix that was applied and landed on this file: research.md R8 corrects an earlier provenance mix-up in which a real `work_item_projection`-view moduledoc fix (commit `92e137e`) was mistakenly believed to be this file's history, when that commit — and the SQLite conversion it belongs to — has since been split onto branch `local-tracker-sqlite` and was never part of `development`. `development`'s own JSON-backed file never carried the stale language in the first place. No documentation change is required to satisfy FR-014.

This conversion has zero coupling to this feature regardless of which branch it lives on — verified by full diff review; the only mention of "Bindle" anywhere in that commit's diff is `store.ex`'s moduledoc disclaiming any relationship.
- FR-017's admission-vs-continuation invariant was verified directly against Symphony's actual code, not assumed: `SymphonyElixir.Tracker.Issue.routable?/2` (`elixir/lib/symphony_elixir/tracker/issue.ex:53-60`) gates on `dispatchable`; `SymphonyElixir.Orchestrator.reconcile_issue_state/4` (`orchestrator.ex:421-441`) and `reconcile_blocked_issue_state/4` (`orchestrator.ex:456-474`) both currently reuse that same predicate to decide whether to terminate a running agent or release a held claim, and `SymphonyElixir.AgentRunner.continue_with_issue?/2` (`agent_runner.ex:174-191`) reuses it a third time to decide whether to continue a multi-turn agent run. Because a durable-claim-aware tracker's `dispatchable` fact naturally goes `false` the moment Symphony's own acquisition (FR-015) succeeds, today's reconciliation would terminate the very execution Symphony just started, on its very next poll — a genuine, verified contradiction between FR-015 (acquire-before-dispatch) and today's continuation logic, not a hypothetical one. By contrast, `should_dispatch_issue?/4` (`orchestrator.ex:823-838`), which calls `candidate_issue?/3` (`orchestrator.ex:860-877`) — the legitimate admission-path usage — is already correctly guarded to apply only to issues not already running, claimed, or blocked, so it requires no change.
- This specification's earlier draft was checked directly against Bindle's actual implementation on 2026-08-27 (`~/Developer/bindle`, `src/bindle/work_ledger.py`, `docs/SYMPHONY.md`, `docs/DECISIONS.md` D037/D038); this rework re-verified those facts and found two of that draft's conclusions needed correction rather than confirmation: (1) the "favor a CLI-emitted artifact" transport leaning is removed (no concrete blocker to a SQL-artifact transport was found, and the user-directed target architecture settles on one); (2) the "synthesize `state` from `(terminal, eligible)`" field-mapping requirement is removed in favor of a direct `status` passthrough, since the corrected projection field shape (FR-002, Key Entities) now specifies a native `status` column rather than the old two-boolean shape. Bindle's real, durable, atomically-arbitrated claim mechanism (`work_item_claims`, `claim()`/`release_claim()`) and its own explicit requirement that "a coordinator MUST still attempt claim() before treating an item as acquired" were the direct evidence motivating FR-015/FR-016, which this specification's prior draft did not previously require.
- **FR-013's task-done/milestone-acceptance distinction (2026-08-27 correction pass) was verified directly against Bindle's current `specs/002-milestone-task-work-items/spec.md`, `docs/DECISIONS.md` D038, `src/bindle/work_ledger.py`, and `contracts/task-write-surface.md`, not assumed.** Bindle's `mark_done()` (`work_ledger.py:986-1007`) is a single guarded `UPDATE work_items SET status='done' ... WHERE id=? AND status='open'` with no claim/ownership check and no cascade to any parent milestone row; D038 states plainly: "Readiness is mechanical; acceptance is semantic... Whether the resulting grouped outcome is actually *accepted* is a human judgment, recorded as an explicit `review → accepted` transition (`accept_milestone()`) the ledger never automates or infers from readiness alone." The `bindle work done <id>` CLI (`contracts/task-write-surface.md`, `symphony_projection.py`'s `complete_task()`) takes no `--owner`/claim argument, rejects a milestone id distinctly (`not_a_task`) rather than silently treating it as a task, and rejects a second call on an already-done task with an explicit `not_open` failure rather than a silent no-op or crash — confirming a task's own `done` transition is safely, narrowly agent-triggerable without any Bindle-side human-review gate, while milestone `accepted` remains a categorically separate, human-only transition Bindle's own model never conflates with it. This is the direct evidence FR-013's correction is grounded in, not an inference from this specification's own prior (overbroad) wording.
