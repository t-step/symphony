# Feature Specification: Bindle-Backed Tracker Adapter Implementation

**Feature Branch**: `003-bindle-tracker-adapter` (Spec Kit feature identifier only; per the fork's workflow — see `001-local-tracker-multi-agent`/`002-bindle-integration` — no separate git branch is created for this feature; work stays on `development`)

**Created**: 2026-08-27

**Status**: Draft (corrected 2026-08-27 — see Correction Note below)

**Input**: User description: "Implement the Bindle-backed Tracker adapter for Symphony as a bounded implementation feature (not another architecture exploration), grounded strictly against specs/002-bindle-integration/ (the frozen, authoritative architecture contract) and independently re-verified against Bindle's actual current implementation and Symphony's actual current source. Scope: (1) a real Bindle Tracker adapter reading Bindle's published read-only SQLite projection; (2) a narrow, optional acquisition/release Tracker callback pair wired into the orchestrator's dispatch/release call sites, with call-site timing, crash recovery, and owner identity resolved as real implementation decisions; (3) a required runtime fix splitting the admission (dispatchable) gate from the continuation/routing gate so a successfully-claimed, now-dispatchable:false item is not preempted, while preserving Linear's and Asana's real per-adapter continuation behavior; (4) an explicit constraint that Bindle's dependency/blocking/milestone/evidence/completion/reconciliation logic is never reconstructed inside Symphony. Includes focused tests using a real temporary SQLite projection fixture and a mockable Bindle-CLI boundary, and an end-to-end proof if feasible. Excludes mechanical evidence verification and any Bindle-side or convenience-UX work."

**Second correction pass (2026-08-27, same day)**: A follow-up pass, triggered by `002-bindle-integration`'s own FR-013 correction (task `done` vs. milestone `accepted`, that spec's research.md R16) plus newly-verified Symphony runtime facts, found five further corrections needed, none of which reopen the architecture boundary: (1) **restored** a narrow, agent-invoked, session-scoped task-`done` tool (FR-025/FR-026) that the first correction pass had removed as if `002-bindle-integration` forbade it entirely — it did not, once corrected; (2) **fixed a retry/claim race**: `retry_candidate_issue?/2` and the acquisition call site must distinguish fresh-admission dispatch from continuation-retry-of-an-already-claimed-issue (FR-016/FR-024), since Bindle rejects a second `claim()` against an already-claimed task even from the same owner; (3) **replaced** the Linear-specific `routed_by_assignment` field/naming with a provider-neutral `continuation_allowed` signal and actually closed Asana's `completed`-vs-section-name gap (FR-013/FR-017), rather than leaving it "documented but open"; (4) **added projection-refresh semantics** (FR-027/FR-028) for the restored `done` tool, since Bindle's `bindle work publish` is a fully separate, manually-triggered step with no auto-publish hook; (5) **fixed startup-reconciliation liveness** (FR-029) so an individual stale-claim release failure gets bounded retries via the existing retry/backoff primitive rather than requiring a full process restart. See `research.md`'s new entries for the full grounding behind each.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Dispatch Bindle-managed work through the existing scheduler, unmodified (Priority: P1)

An operator configures a Symphony deployment with `tracker.kind: bindle` pointing at a Bindle repository's published projection artifact. Symphony polls it exactly like any other tracker, sees a dispatchable task, and the orchestrator/agent-runner path handles it with no code path aware it originated from Bindle.

**Why this priority**: Without a working adapter that produces a correct `Tracker.Issue`, nothing else in this feature has a caller — this is the feature's entire reason to exist, and it is the seam `002-bindle-integration` FR-001/FR-002/FR-004 already fixed the contract for.

**Independent Test**: Point `tracker.kind: bindle` at a real (or fixture) `symphony-projection.sqlite3` containing one dispatchable `task_projection` row; confirm Symphony's tracker adapter returns a `Tracker.Issue` with the correct fields populated and every other field at its struct default, using only the six existing `Tracker` callbacks — no new orchestrator-facing type or module.

**Acceptance Scenarios**:

1. **Given** a published projection with one dispatchable row (`id`, `identifier`, `title`, `description`, `status = "open"`, `dispatchable = 1`, `created_at`), **When** the Bindle adapter's `fetch_issues_by_states/1` or `fetch_issues_by_ids/1` is called, **Then** it returns a `Tracker.Issue` with `id`, `identifier`, `title`, `description` populated verbatim, `state` set from `status` with no synthesis, `dispatchable: true`, `created_at` parsed, and every other `Issue` field (`native_ref`, `priority`, `branch_name`, `url`, `assignee_id`, `labels`, `blocked_by`, `updated_at`) left at its existing struct default.
2. **Given** the projection file does not exist, has a `PRAGMA user_version` other than the one value this adapter supports, or cannot be opened, **When** the adapter attempts a read, **Then** it returns a distinguishable `{:error, _}` result Symphony's existing tracker/source failure handling already tolerates (skip this poll tick, retry next), never a partial or silently-misread result and never a crash.
3. **Given** the adapter is configured, **When** it opens the projection artifact, **Then** it does so using SQLite's own read-only open mode, issues no write/migration/repair statement against it under any code path, and never opens any file other than the one configured projection path (in particular, never a Bindle canonical ledger file).
4. **Given** a projection row that is structurally missing a field Symphony requires to schedule it at all (a null/empty `id`, `identifier`, `title`, or `status`, or an unparseable `created_at`), **When** the adapter maps that row, **Then** it returns a distinguishable `{:error, _}` for the affected fetch rather than silently dropping the row and returning the remaining rows as if the malformed one never existed — an upstream `dispatchable: true` task MUST NOT silently become invisible to Symphony because the adapter's own row-shape validation quietly filtered it out.

### User Story 2 - Real dispatch-time claim arbitration, not a trusted snapshot (Priority: P1)

An operator running Symphony against Bindle-managed work needs Symphony to never treat two workers — two poll cycles, or in a future multi-instance deployment, two processes — as having acquired the same Bindle task, even though the projection's `dispatchable` fact is a periodically-refreshed snapshot that can be stale by the time Symphony actually dispatches.

**Why this priority**: This is `002-bindle-integration` FR-015/FR-016's load-bearing seam. Without it, `dispatchable: true` would be silently treated as a durable acquisition guarantee it was never designed to be.

**Independent Test**: Seed two concurrent dispatch attempts against the same dispatchable Bindle task (via a stubbed CLI boundary that lets exactly one "win"); confirm exactly one acquisition succeeds and the other is treated as "not currently available" — skipped, not an error, crash, or alert.

**Acceptance Scenarios**:

1. **Given** a Bindle task whose projection record reads `dispatchable: true`, **When** the orchestrator is about to dispatch it, **Then** it calls the adapter's `acquire_issue/2` callback immediately before spawning the coding-agent `Task`, supplying neither a worktree nor a branch parameter to the underlying claim (the real workspace does not exist yet at this point, and Bindle's own reconciliation treats a supplied worktree path as a literal, checkable filesystem/Git-worktree location — inventing one here would create false staleness findings on Bindle's side), and only proceeds to spawn on a successful (`:ok`) result; any other result skips dispatching that item this cycle, exactly as an ordinary failed `candidate_issue?/3` check does today.
2. **Given** the acquisition callback's underlying call is Bindle's own `bindle work claim <id> --owner <owner>` CLI invocation, **When** two concurrent attempts race for the same task, **Then** Bindle's own claim arbitration (a single-row insert keyed on the task id) guarantees exactly one succeeds; the loser's non-zero exit is mapped to `{:error, _}`, never raised or crashed on.
3. **Given** an issue that has already been dispatched and is now running or blocked, **When** it reaches any of the orchestrator's existing claim-release points for an already-dispatched issue (retry-exhausted after the worker actually ran, terminal-state transition, routed-away, missing-issue detection), **Then** the orchestrator calls `release_issue/2` at that same point — and does **not** call it merely because a retry is scheduled for a worker that already started and is intentionally reusing its existing workspace/branch across retry backoff.
4. **Given** acquisition succeeds but the orchestrator's own subsequent attempt to start the coding-agent worker fails before any workspace or attempt exists (e.g. the worker-supervisor rejects spawning the process) — a fundamentally different case from Scenario 3, since no workspace was ever created and nothing is being reused — **When** that spawn failure occurs, **Then** the orchestrator calls `release_issue/2` as immediate compensation before scheduling the ordinary spawn-failure retry, so the external Bindle claim is not left held by a dispatch attempt that never actually started.
5. **Given** every tracker adapter that does not implement `acquire_issue/2`/`release_issue/2` (asana, github, gitlab, jira, linear, local), **When** the orchestrator dispatches or releases an issue from one of those trackers, **Then** its behavior is unchanged, byte-for-byte, from before this feature — the callback pair is a complete no-op for it.
6. **Given** a Symphony process crash at any point after a successful acquisition but before that task's coding-agent run is fully underway, **When** Symphony next starts up, **Then** startup-time reconciliation attempts a release for every task currently visible in the Bindle-facing projection using this deployment's persisted owner identity, before resuming normal polling — relying on Bindle's own safe-release guarantee (releasing a task not claimed by this owner is a no-op) rather than requiring Symphony to have separately recorded which tasks it previously claimed.

### User Story 3 - A just-claimed task is not preempted on the very next poll (Priority: P1)

An operator needs a Bindle task Symphony has successfully claimed and started executing to keep running even though the next poll's projection record for that same task now reads `dispatchable: false` — the expected, ordinary result of Bindle correctly reporting a claimed item as unavailable to other acquirers.

**Why this priority**: This is the required runtime correctness fix (`002-bindle-integration` FR-017). Without it, the ordinary claim-then-dispatch sequence User Story 2 requires causes Symphony's own reconciliation to terminate the execution it just started, on the very next poll — a genuine, verified contradiction, not a hypothetical one, since `Orchestrator.reconcile_issue_state/4`, `reconcile_blocked_issue_state/4`, and `AgentRunner.continue_with_issue?/2` all three currently gate continuation on the same combined `Issue.routable?/2` predicate that includes `dispatchable`.

**Independent Test**: Drive a running (or blocked) issue through reconciliation with a refreshed `Issue` whose `dispatchable` is `false` but whose `state` is still active and whose routing/label match is unchanged; confirm the running agent is NOT terminated and the held claim/block is NOT released, while confirming a terminal-state transition, a non-active state, or the issue disappearing from the tracker's visible set still terminates/releases exactly as before.

**Acceptance Scenarios**:

1. **Given** a running issue whose refreshed projection record now has `dispatchable: false` but an unchanged active `state` and unchanged routing (labels still match; for adapters with an assignment signal, still assigned to this worker), **When** `Orchestrator.reconcile_issue_state/4` runs, **Then** it does not terminate the running agent — reconciliation must consult only the continuation/routing concern, never `dispatchable`, for this decision.
2. **Given** the same scenario for a blocked issue, **When** `Orchestrator.reconcile_blocked_issue_state/4` runs, **Then** it does not release the held block.
3. **Given** the same scenario mid-run, **When** `AgentRunner.continue_with_issue?/2` evaluates whether to continue a multi-turn agent run, **Then** it returns `{:continue, _}`, not `{:done, _}`, on `dispatchable` alone.
4. **Given** an issue that moves to a terminal state, moves to a non-active state, is no longer routed to this worker (label mismatch, or — for Linear — reassigned to someone else), or disappears entirely from the tracker's fetched set, **When** reconciliation runs, **Then** it still terminates the running agent / releases the held block exactly as it does today — this fix narrows only the role `dispatchable` plays, and changes none of these other checks.
5. **Given** the legitimate admission-path usage in `candidate_issue?/3` (via `should_dispatch_issue?/4`, already scoped to issues not already running/claimed/blocked), **When** this feature's fix is applied, **Then** that code path is unchanged — `dispatchable` continues to gate whether an issue not already running/claimed/blocked may be newly dispatched.

### User Story 4 - Every existing tracker's behavior is provably unchanged (Priority: P2)

An operator running Symphony against GitHub, GitLab, Jira, Linear, Asana, or the standalone local tracker needs certainty that adding the Bindle adapter and the admission/continuation fix changes nothing about how their own deployment already behaves — including subtle existing behaviors like Linear's assignee-reassignment continuation stop and Asana's `completed`-vs-section-name handling.

**Why this priority**: `002-bindle-integration`'s entire premise (FR-004, Constitution II/VII) is that this integration adds no Bindle-specific branch to shared orchestration code and regresses nothing. This story is the regression-safety net the other stories' changes are checked against.

**Independent Test**: Run each existing adapter's current dispatch/continuation/release test coverage unmodified in outcome (tests may be extended, not weakened) before and after this feature's changes; confirm identical pass/fail behavior, with Linear's and Asana's specific continuation semantics re-verified explicitly rather than assumed preserved.

**Acceptance Scenarios**:

1. **Given** Linear's adapter populates an issue-still-assigned-to-this-worker signal today, **When** that signal goes false (reassigned) for a running issue, **Then** continuation still stops for that reason, unaffected by this feature's split of admission from routing.
2. **Given** Asana's adapter's existing `completed`-vs-section-name gap (confirmed real: `state` derives solely from section name, `dispatchable` solely from `task["completed"]`/`resource_subtype`, with no code tying the two together), **When** this feature's changes are applied, **Then** the gap is actually closed — Asana populates `continuation_allowed` from `task["completed"] == false`, independent of section/state, so a task that completes without its section changing correctly stops continuation (FR-017/SC-010) — not merely documented as a known, accepted trade-off.
3. **Given** any of the six existing adapters, **When** the orchestrator dispatches or releases an issue from it, **Then** `acquire_issue/2`/`release_issue/2` are never called against it in a way that changes observable behavior (the callback pair is optional and unimplemented for all six).

### User Story 5 - An agent may report its own bound task done; Bindle's milestone/dependency/evidence model stays inside Bindle (Priority: P3, corrected 2026-08-27 — see Correction Note)

A team integrating Bindle-managed work needs assurance that this feature does not quietly grow into a second place where Bindle's dependency/blocking, milestone, evidence, or reconciliation logic is reconstructed or decided, or where milestone acceptance is inferred from mechanical signals — while also having the one narrow, genuinely useful capability Bindle's own model explicitly authorizes without human review: an agent working its own bound Bindle task reporting, on its own explicit initiative, that its execution work is done. `002-bindle-integration` FR-013 (as corrected) draws this line precisely: Symphony/an agent MUST NOT infer semantic correctness or automate milestone acceptance from mechanical evidence, but an agent MAY explicitly request its own bound task's ordinary `done` transition through the existing tracker-write boundary — Bindle's own model does not gate that specific transition on human review.

**Why this priority**: Lower priority than the runtime seam itself, but explicitly called out because the natural failure mode in either direction is easy to reach for: either quietly letting "just one more" Bindle-aware capability creep in (evidence checking, milestone review, dependency awareness) until the boundary `002-bindle-integration` fixed erodes, or overcorrecting by refusing the one capability Bindle's own model safely authorizes and that the first correction pass mistakenly removed.

**Independent Test**: Confirm the only Bindle-owned write operations this feature's code calls anywhere are `bindle work claim`, `release`, `done`, and `publish` (the last two reachable only from the one narrow agent-invoked task-completion tool, never from the orchestrator-owned claim/release seam); confirm this feature exposes exactly one agent-invoked tool, scoped to the session's own bound task id and incapable of targeting any other task; confirm no code path anywhere reads or interprets Bindle's dependency, blocking, milestone, or evidence tables/columns, and no code path calls or exposes any milestone review/acceptance operation.

**Acceptance Scenarios**:

1. **Given** this feature's full implementation, **When** inspected for any tool touching a Bindle-managed item's lifecycle state, **Then** exactly one exists — the agent-invoked task-completion tool (FR-025/FR-026) — and it is scoped exclusively to the one task bound to the requesting session; no orchestrator-owned API for marking a task done exists, and no tool of any kind can record evidence, touch dependency/blocking state, or reach milestone review/acceptance.
2. **Given** a coding-agent session working a Bindle-managed task finishes its execution work, **When** the agent explicitly invokes the task-completion tool, **Then** Symphony calls `bindle work done <id>` for exactly that session's bound task id (never a different id the model's tool-call arguments might supply) followed by a best-effort `bindle work publish` (FR-027) — and this is the full extent of the capability; the agent cannot use this tool to affect any other task or any milestone.
3. **Given** this feature's full implementation, **When** reviewed against `002-bindle-integration`'s Non-Goals and corrected FR-013, **Then** no dependency graph, milestone concept, evidence-validation logic, reconciliation policy, or milestone-acceptance automation has been introduced inside Symphony — the one capability that does exist (task `done`) is an explicit, scoped, agent-initiated report of the agent's own finished work, not an inference either system draws from mechanical signals.

### Edge Cases

- What happens when the projection artifact is temporarily unreachable during a poll or reconciliation pass? Symphony MUST treat this the same as any other tracker/source outage — skip the affected poll tick or reconciliation pass, retry next, leave already-running attempts undisturbed (`002-bindle-integration` FR-008).
- What happens when the `bindle` CLI binary is not on `$PATH`, or the configured Bindle repository path does not exist? `acquire_issue/2`/`release_issue/2` MUST return `{:error, _}` distinguishably (e.g. `{:error, {:bindle_cli_unavailable, _}}`), never crash the orchestrator process; this is treated as an acquisition/release failure, not a work-item attempt failure.
- What happens when Symphony restarts after a run that crashed mid-attempt, possibly leaving a Bindle claim held? Startup-time reconciliation MUST enumerate every task currently visible in the Bindle-facing projection and attempt an owner-scoped release for each, before resuming normal polling — Symphony does not need its own separate record of which tasks it previously claimed, because Bindle's release is a safe no-op for any task this deployment's owner identity did not actually hold. If the projection itself cannot be read or fails its schema-version check at this moment, startup MUST surface that as the same distinguishable tracker/source failure an ordinary poll failure would produce, rather than silently skipping recovery or silently proceeding as if nothing needed releasing.
- What happens if `release_issue/2`'s underlying CLI call itself fails (e.g. Bindle process unreachable at release time)? The orchestrator's in-memory release bookkeeping MUST proceed regardless — a release-call failure is logged, never allowed to leave Symphony's own in-memory state stuck holding a claim it believes it should have released; the resulting Bindle-side stale claim is recovered by the startup-time reconciliation above on next restart, not retried synchronously.
- What happens when acquisition succeeds but the subsequent attempt to start the coding-agent worker itself fails (the worker-supervisor rejects spawning, before any workspace exists)? This is not the "retry reuses an existing workspace/branch" case — no workspace was ever created — so the orchestrator MUST release the just-acquired claim as compensation before scheduling the ordinary spawn-failure retry, otherwise the retry's own future acquisition attempt would be rejected by Bindle as already claimed by this same owner, deadlocking that issue against itself.
- What happens when two Bindle tasks resolve to the same computed workspace key (identifier collision)? Out of scope for this feature — `002-bindle-integration`'s Key Entities require `identifier` be unique within its configured tracker scope, same as every existing adapter; this feature does not add new collision handling beyond what already exists.
- What happens when a retry is scheduled for an issue whose worker already started and is intentionally reusing its existing workspace/branch (the worker crashed mid-run but Bindle's claim is still held)? `release_issue/2` MUST NOT be called merely because this kind of retry is scheduled — the same workspace/branch and the same Bindle claim are intentionally reused across retry backoff (`002-bindle-integration` FR-015). This is explicitly distinct from the spawn-failure case above, where no workspace/attempt exists yet to reuse.
- What happens when that same crash-mid-run retry reaches its own re-validation and dispatch step? It MUST be treated as a **continuation retry**, not fresh admission (FR-016/FR-024): re-validation MUST NOT require `dispatchable = true` (the retained claim makes it `false` by construction), and `spawn_issue_on_worker_host/5` MUST NOT call `acquire_issue/2` again — Bindle rejects a second `claim()` against an already-claimed task even from the same owner, so an unconditional re-acquire at this shared call site would permanently deadlock the retry against itself.
- What happens if the agent-invoked task-completion tool (FR-025/FR-026) is called with a tool-call argument naming a task id other than the session's own bound task? The tool MUST ignore any model-supplied id entirely and resolve the target exclusively from the session's own bound `Tracker.Issue` — there is no code path by which a coding-agent session can mark any task other than its own bound task done, regardless of what arguments the model supplies.
- What happens when the task-completion tool's `bindle work done <id>` call succeeds but the immediately-following `bindle work publish` call fails? The `done` transition MUST be treated as successful and MUST NOT be retried — Bindle's `mark_done/1` guard (`status = 'open'`) would reject a repeated call with a spurious `not_open` failure, since the real mutation already succeeded. The publish failure MUST be surfaced as its own, distinctly-logged failure (FR-027); this feature does not add automatic retry-until-success publish logic beyond this one best-effort attempt — a projection that stays stale until the next successful publish (whether Bindle's own operator-run cadence, or this task's own next Symphony-initiated mutation) is an accepted, explicitly-documented limitation, not a silent gap.
- What happens when an individual task's owner-scoped release fails during startup-time reconciliation (FR-012)? It MUST NOT be left unretried until the next full process restart (FR-029): Symphony schedules a bounded number of follow-up retries for exactly that id, reusing the existing issue-retry timer/backoff primitive, while normal polling begins immediately and is not blocked by these follow-up retries. If the bounded retry budget is exhausted, Symphony MUST log a persistent, operator-visible failure naming the task id rather than silently treating the claim as recovered.
- What happens if an operator configures `tracker.kind: bindle` with a Bindle repository path that has never published a projection (`.bindle-work/symphony-projection.sqlite3` absent)? This MUST be handled identically to "projection unreadable" above — a clear, operator-visible tracker/source failure, not a crash and not an empty-but-successful poll.
- What happens if this deployment's persisted owner-identity storage exists but is corrupt or empty (as opposed to simply never having been created yet)? Symphony MUST fail loud — a configuration/startup error, never a silently-generated replacement identity — since generating a new identity would permanently orphan any claim already made under the original one, with no local record connecting the two.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Symphony MUST provide a new `SymphonyElixir.Bindle.Adapter` module implementing the `SymphonyElixir.Tracker` behaviour, registered under a new `"bindle"` key in `SymphonyElixir.Tracker.@adapters`, following the same per-adapter package convention as `local/`, `github/`, `gitlab/`, `jira/`, `linear/`, `asana/`.
- **FR-002**: The Bindle adapter's `fetch_issues_by_states/1` and `fetch_issues_by_ids/1` MUST read only the configured Bindle-published projection artifact (a physically separate SQLite file from any Bindle canonical ledger file), opened exclusively via SQLite's own read-only open mode, and MUST validate the artifact's schema-version marker before trusting its contents; an incompatible version, missing file, or unreadable artifact MUST produce a distinguishable `{:error, _}` result, never a partial or silently-misread one, and MUST route through Symphony's existing tracker/source failure handling (skip poll tick, retry next).
- **FR-003**: The Bindle adapter MUST map each projection row onto `Tracker.Issue` by column name (never positionally), passing published values through verbatim without synthesizing any missing value: `status` passes through to `state` with no synthesis; `dispatchable` passes through verbatim; `id`, `identifier`, `title`, `description`, `created_at` pass through verbatim; every other `Issue` field not published by the projection (`native_ref`, `priority`, `branch_name`, `url`, `assignee_id`, `labels`, `blocked_by`, `updated_at`) is left at its existing struct default. Each returned row MUST be validated against the minimum shape Symphony requires to schedule it at all (non-empty `id`/`identifier`/`title`/`status`, a parseable `created_at`); a row failing this validation MUST cause the affected fetch to return a distinguishable `{:error, _}`, never a silently-dropped row folded into an otherwise-successful result — `{:ok, []}` is reserved for a genuinely empty query result, never for "rows existed but were malformed."
- **FR-004**: The Bindle adapter MUST NOT under any circumstance create, migrate, or repair the projection artifact, and MUST NOT open any Bindle-owned database file other than the one configured projection path.
- **FR-005**: `SymphonyElixir.Tracker` MUST gain one new, narrow, `@optional_callbacks`-guarded pair — `acquire_issue/2` and `release_issue/2` — with a shape carrying no adapter-specific vocabulary, such that every one of the six existing adapters (asana, github, gitlab, jira, linear, local) that does not implement them is completely unaffected, byte-for-byte.
- **FR-006**: The orchestrator MUST call the active adapter's `acquire_issue/2`, when implemented, immediately before spawning the coding-agent `Task` for a candidate issue, and MUST only proceed to spawn on a successful result; any other result MUST skip dispatching that issue for the current poll cycle without crashing or alerting, exactly as an ordinary failed admission check does today. This call MUST NOT supply a worktree or branch value that is not yet truthfully known — no post-claim metadata-enrichment mechanism is required or added by this feature.
- **FR-007**: The orchestrator MUST call the active adapter's `release_issue/2`, when implemented, at every existing point it releases its own claim/block bookkeeping for an issue that has already been dispatched (retry-exhausted after the worker actually ran, terminal-state transition, routed-away, missing-issue detection) — and MUST NOT call it solely because a retry is being scheduled for a worker that already started and is intentionally reusing its existing workspace/branch across retry backoff.
- **FR-008**: If `acquire_issue/2` succeeds but the orchestrator's own subsequent attempt to start the coding-agent worker fails before any workspace or attempt exists, the orchestrator MUST call `release_issue/2` as immediate compensation before scheduling the resulting spawn-failure retry — this is a distinct case from FR-007's retry exemption, since no workspace exists yet to reuse and, without this compensation, the retry's own next acquisition attempt would be rejected by Bindle as already claimed by this same owner.
- **FR-009**: The Bindle adapter's implementation of `acquire_issue/2`/`release_issue/2` MUST call only Bindle's own supported CLI write surface (`bindle work claim`, `bindle work release`) — reading the CLI's exit code and stderr/stdout output per its own documented exit-code convention — and MUST NOT issue a raw SQL mutation against any Bindle-owned database file, canonical or published.
- **FR-010**: The Bindle adapter MUST invoke the `bindle` CLI with its working directory (`cwd`) set to the operator-configured Bindle repository path, since the CLI resolves its target ledger from the invoking process's current working directory and accepts no repository-path flag.
- **FR-011**: Symphony MUST define and persist a stable, deployment-local owner-identity string used as the `--owner` argument to every `bindle work claim`/`release` call, reused across restarts of the same deployment (new state; nothing existing is repurposed for this). If this identity's persisted storage exists but is corrupt or empty, Symphony MUST fail loud rather than silently generate a replacement — regenerating it would permanently orphan any claim already made under the original identity.
- **FR-012**: Symphony MUST perform startup-time reconciliation, before resuming normal polling, that enumerates every task id currently visible in the Bindle-facing projection and issues an owner-scoped `bindle work release` call for each, using this deployment's persisted owner identity — relying on Bindle's own safe-release guarantee (a release call for a task not claimed by this owner, including an already-unclaimed task, is a no-op) rather than requiring Symphony to separately track which tasks it previously claimed. If the projection cannot be read or fails its schema-version validation at this point, this reconciliation MUST surface the same distinguishable tracker/source failure FR-002 defines rather than silently skipping recovery or silently proceeding.
- **FR-013**: `SymphonyElixir.Tracker.Issue`'s combined admission-and-routing predicate (currently `routable?/2`) MUST be split into two distinct concerns: an admission concern (`dispatchable` alone) and a continuation/routing concern (label match, plus a new, provider-neutral `continuation_allowed` signal — default `true` — for adapters that populate it with an independent, provider-specific fact that continuation should stop even though label match alone would not catch it, such as Linear's still-assigned-to-this-worker check or Asana's task-completed check; see FR-017).
- **FR-014**: `Orchestrator.reconcile_issue_state/4` and `Orchestrator.reconcile_blocked_issue_state/4` MUST consult only the continuation/routing concern (FR-013), never `dispatchable`, when deciding whether to terminate a running agent or release a held block for an issue Symphony already has running/blocked state for.
- **FR-015**: `AgentRunner.continue_with_issue?/2` MUST consult only the continuation/routing concern (FR-013), never `dispatchable`, when deciding whether a multi-turn agent run continues.
- **FR-016**: The admission-path usage in `Orchestrator.candidate_issue?/3` (reached only via `should_dispatch_issue?/4`, already scoped to issues not already running, claimed, or blocked) MUST remain gated on `dispatchable` and MUST NOT be altered by FR-013's split. This is the **fresh-admission** mode: it applies only to an issue not already present in `state.claimed`. Symphony's dispatch/retry re-validation path (`revalidate_issue_for_dispatch/3`/`retry_candidate_issue?/2`, reached through `refresh_issue_for_dispatch/1`, which is shared by both the fresh-dispatch path (`dispatch_issue/4`) and the retry-continuation path (`handle_active_retry/4`)) MUST distinguish two modes rather than applying one uniform check to both: **Fresh admission** — the issue is not already present in `state.claimed` (a first dispatch attempt, or a retry following FR-008's spawn-failure compensation release) — MUST continue to require `dispatchable = true`, exactly as today. **Continuation retry** — the issue is already present in `state.claimed` because a prior worker for it actually started (an ordinary crash-mid-run retry reusing its existing workspace/branch, FR-007) — MUST NOT require `dispatchable = true`; re-validation for this mode MUST instead use only the continuation/routing concern (FR-013) plus the existing terminal/active/missing-from-tracker checks, the same checks ordinary reconciliation (FR-014/FR-015) already uses. Without this split, a continuation retry of a Bindle task Symphony already holds a claim for would be rejected at this re-validation step — since a claimed Bindle task's `dispatchable` fact is `false` by construction (data-model.md §1) — even before reaching the acquisition call site FR-024 governs.
- **FR-017**: This feature's fix (FR-013–FR-016) MUST preserve every existing adapter's real current continuation behavior, verified directly rather than assumed. In particular: Linear's existing assignee-reassignment continuation stop MUST be preserved unchanged, carried forward as `continuation_allowed`'s value for Linear (FR-013). Asana's `completed`-vs-section-name gap — confirmed real and structurally possible, not merely hypothetical (`asana/client.ex`: `state` derives from `memberships.section.name` alone, `dispatchable` derives from `task["completed"]`/`resource_subtype` alone, with no code tying the two together, so a task can flip `completed: true` while its section name, and therefore `state`, stays unchanged) — MUST be actually fixed by this feature via Asana's own `continuation_allowed` population (FR-013), not merely documented as a dropped or deferred trade-off; this feature MUST NOT ship leaving this gap open when a fix (independent, direct population from `task["completed"]`) is this straightforward and already required by FR-013's field addition.
- **FR-018**: `acquire_issue/2`/`release_issue/2` MUST be scoped exclusively to Bindle's claim/release CLI calls — MUST NOT read or write any lifecycle-state field, MUST NOT call `bindle work done` or any other lifecycle-mutating operation, and MUST NOT be satisfiable by a raw database mutation.
- **FR-019** (corrected 2026-08-27 — see Correction Note): This feature MUST NOT introduce any new **orchestrator-owned** tool or API that mutates a Bindle-managed item's lifecycle state — the orchestrator-owned claim/release seam (FR-005–FR-009) remains scoped exclusively to claim/release (FR-018) and never lifecycle state. This feature also MUST NOT introduce any tool, agent-invoked or otherwise, that touches Bindle's milestone review/acceptance operations, dependency/blocking graph, or evidence tables — `002-bindle-integration` FR-013's corrected semantic-judgment boundary means passing mechanical checks never authorizes a milestone-acceptance decision, and no capability this feature adds reaches anywhere near that boundary. This does not forbid the one narrow, agent-invoked, session-scoped task-completion tool FR-025/FR-026 restore: `002-bindle-integration` FR-013 (as corrected) explicitly authorizes an agent's own bound-task `done` request through the existing `agent_tool_specs/0`/`execute_agent_tool/3` boundary, and this feature's FR-025/FR-026 build exactly that, no more — this is a clarification of scope, not a new orchestrator-owned API.
- **FR-020**: The `release_issue/2` counterpart MUST be satisfiable at every existing orchestrator release call site, including any site where only the issue's stable id — not a full `Tracker.Issue` struct — is available at that point in the code; this feature MUST NOT fabricate a partial or synthetic `Issue` merely to satisfy a callback shape that assumed a full struct is always available. `acquire_issue/2` MAY continue to receive the full candidate `Issue`, since the full struct is always genuinely available wherever acquisition is called.
- **FR-021**: Each logical release event (retry-exhausted, terminal-state transition, routed-away, missing-issue detection, or the spawn-failure compensation in FR-008) MUST result in exactly one external `release_issue/2` call — never zero, and never more than one for the same event even where the orchestrator's existing code routes through more than one internal function to handle that event.
- **FR-022**: Selecting `tracker.kind: bindle` MUST be a distinct, explicit configuration choice, mutually exclusive with every other `tracker.kind` value, consistent with the existing single-active-work-tracking-source model (`001-local-tracker-multi-agent` FR-012).
- **FR-023** (corrected 2026-08-27 — see Correction Note): This feature MUST NOT reconstruct, cache, or become authoritative for any Bindle dependency/blocking graph, milestone concept, or evidence-validation logic inside Symphony, and MUST NOT infer semantic correctness or milestone acceptance from any signal — those remain resolved only through Bindle's own supported interfaces, by a human or by Bindle itself, never by this feature. The one narrow exception is task-level execution completion (`done`): FR-025/FR-026 restore a session-scoped, agent-invoked tool that requests Bindle's own `bindle work done <id>` on the agent's explicit instruction — this is Bindle's own supported task-lifecycle write, authorized by `002-bindle-integration` FR-013 as corrected, not a reconciliation policy or a semantic-correctness judgment Symphony makes on the agent's behalf; the agent, not Symphony, is the one asserting the fact.
- **FR-024**: Symphony's dispatch/retry re-validation and acquisition call sites MUST distinguish fresh-admission dispatch from continuation-retry dispatch (FR-016). The orchestrator's acquisition call site (`spawn_issue_on_worker_host/5`, FR-006) MUST call `acquire_issue/2` only in fresh-admission mode — i.e. only when the issue is not already present in `state.claimed`. For a continuation retry of an issue already present in `state.claimed` because a prior worker for it actually started, `spawn_issue_on_worker_host/5` MUST NOT call `acquire_issue/2` again — it MUST proceed directly to `Task.Supervisor.start_child/2`, reusing the already-held Bindle claim. This is a correctness requirement, not an optimization: Bindle's `work_item_claims` primary key is `work_item_id` alone, not `(work_item_id, owner)` — a second `claim()` call against an already-claimed task is rejected even from the same owner (`already_claimed`), never treated as a no-op. Calling `acquire_issue/2` unconditionally at this shared call site would permanently deadlock every continuation retry of a Bindle-claimed task against its own retry, since the retry's own acquisition attempt would always be rejected.
- **FR-025**: Symphony MUST provide one new, narrow, agent-invoked tool for the Bindle-backed tracker — exposed through the adapter's existing `agent_tool_specs/0`/`execute_agent_tool/3` boundary, mirroring the standalone local tracker's `local_tracker_set_state` scope-restriction pattern — that marks the ONE Bindle task bound to the current coding-agent session `done`. It MUST NOT accept a model-supplied task id as its target; it MUST resolve the target exclusively from the session's own bound `Tracker.Issue`, available in `execute_agent_tool/3`'s `opts` via the existing per-run MCP binding `SymphonyElixir.ClaudeCode.MCPServer` already establishes (verified: the bound `issue` is fixed at that listener's `start_link/1` time, not read from any model-supplied argument) — so this tool cannot target any Bindle task other than the one bound to that session, regardless of what a coding agent's own tool-call arguments claim.
- **FR-026**: This tool's implementation MUST call only Bindle's supported `bindle work done <id>` CLI operation (via a new `done/3` function on `SymphonyElixir.Bindle.Cli`, mirroring `claim/4`/`release/4`'s existing shape) and MUST NOT infer task completion from test results, mechanical evidence, process exit codes, or any other automatic signal — it fires exclusively in direct response to the agent's own explicit tool call. It MUST NOT expose, wrap, or provide any path to Bindle's milestone review/acceptance operations, and MUST NOT introduce a new orchestrator-owned lifecycle-write API — this is an agent-invoked write through the existing `agent_tool_specs/0`/`execute_agent_tool/3` boundary (`002-bindle-integration` FR-009/FR-013), not an orchestrator-owned one, and is distinct from — and MUST NOT be confused with, sharing no code path with — the orchestrator-owned `acquire_issue/2`/`release_issue/2` seam (FR-005–FR-009, FR-018), which remains scoped exclusively to claim/release.
- **FR-027**: Immediately after a successful `bindle work done` invocation, this tool's implementation MUST invoke `bindle work publish` (via a new `publish/2` function on `SymphonyElixir.Bindle.Cli`) as a best-effort projection refresh, so the task's completion becomes visible through the published projection without requiring an undocumented manual `bindle work publish` step by an operator (Bindle's own write surface has no `--publish` flag or auto-publish hook on any lifecycle-mutating command — verified directly against `src/bindle/cli.py`). A publish failure after a successful `done` MUST be surfaced as a distinct, separately-logged failure — MUST NOT be treated as a `done` failure, and MUST NOT trigger a retry of the `done` call itself, since Bindle's `mark_done/1` guard (`status = 'open'`) makes a repeated `done` call after a real prior success return a spurious `not_open` rejection, not a safe no-op or a meaningful retry.
- **FR-028**: `acquire_issue/2` and `release_issue/2` (the orchestrator-owned claim/release seam, FR-005–FR-009) MUST NOT call `bindle work publish`. Their correctness is already guaranteed by Bindle's durable, atomically-arbitrated claim mechanism (`work_item_claims`' primary-key constraint) independent of the published projection's own refresh cadence — verified directly that `claim()`/`release_claim()` never call `publish()` internally, and that projection staleness affects only what an external reader currently sees, never whether a concurrent claim attempt is correctly arbitrated. This feature MUST NOT add a `publish` call at every claim/release without a demonstrated correctness need for one.
- **FR-029**: Symphony's startup-time reconciliation sweep (FR-012) MUST NOT leave an individual owner-scoped `bindle work release <id>` failure unretried until the next full process restart. If any release call in the sweep fails, Symphony MUST schedule a bounded number of follow-up retry attempts for exactly the ids that failed, reusing the same timer/backoff scheduling primitive the orchestrator's existing issue-retry mechanism (`schedule_issue_retry/4`) already uses, rather than introducing a new scheduling mechanism or a local claims ledger (`002-bindle-integration` Out of Scope; this feature's own data-model.md §6). Normal polling MUST begin immediately after the sweep's initial pass and MUST NOT be blocked waiting on these follow-up retries — an unrecovered stale claim for one task MUST NOT prevent dispatch of any other dispatchable task. If the bounded retry budget is exhausted without success for a given id, Symphony MUST log this as a persistent, operator-visible failure naming the specific task id; it MUST NOT be silently dropped, and this feature's own documentation MUST NOT claim such a stale claim was "recovered without manual intervention" when this is the actual outcome.

### Key Entities

- **Bindle-Facing Schedulable Projection** (existing, published by Bindle — read, not created, by this feature): the physically separate, read-only SQLite artifact at the operator-configured path (conventionally `<repo_path>/.bindle-work/symphony-projection.sqlite3`), containing one `task_projection` row per top-level schedulable Bindle task — present regardless of that task's claim state, with only its `dispatchable` fact changing once claimed — with a schema-version marker this feature's adapter must validate before use.
- **Bindle-Backed Tracker Adapter** (new, this feature): `SymphonyElixir.Bindle.Adapter`, structurally analogous to the existing per-provider adapters, reading only the projection above and calling only Bindle's supported CLI write surface for acquisition/release.
- **Tracker Acquisition/Release Seam** (new, this feature, on the existing `Tracker` behaviour): the `acquire_issue/2`/`release_issue/2` optional callback pair and its orchestrator call sites, including the acquire-success/spawn-failure compensation path (FR-008).
- **Bindle CLI Write Surface** (existing, external to Symphony): Bindle's own supported `bindle work claim`/`release`/`done`/`publish` commands. The orchestrator-owned claim/release seam (FR-005–FR-009, FR-018) invokes only `claim` and `release`, as an external process with `cwd` set to the target Bindle repository, whose exit code and output this feature's adapter interprets but never bypasses with a direct database write — it never invokes `done` or `publish` (FR-018). Separately, the new agent-invoked task-completion tool (FR-025/FR-026) invokes only `done`, immediately followed by a best-effort `publish` (FR-027) — a distinct code path from the claim/release seam, sharing only the `SymphonyElixir.Bindle.Cli` wrapper module. Neither path invokes Bindle's milestone review/acceptance operations; no such operation is part of this Key Entity.
- **Owner Identity** (new, this feature): a stable, deployment-local identifier persisted across restarts, supplied as every claim/release call's `--owner` argument, including startup-time reconciliation's blind, safe-release attempts across every task the current projection lists. Corrupt/empty persisted state is a fail-loud configuration error, never silently regenerated (FR-011). Not used by the `done`/`publish` calls (FR-026/FR-027) — Bindle's `bindle work done`/`publish` CLI take no `--owner` argument (verified against `contracts/task-write-surface.md`/`symphony_projection.py`'s `complete_task()`).
- **Continuation/Routing Concern** (new split of an existing concept, this feature): the subset of `Tracker.Issue`'s existing fields — labels, plus a new, provider-neutral `continuation_allowed: boolean()` field (default `true`) — that governs whether Symphony continues an already-dispatched issue, now explicitly distinct from the admission concern (`dispatchable`). `continuation_allowed` replaces the earlier, Linear-specific `routed_by_assignment` naming/semantics (corrected 2026-08-27, see Correction Note): Linear populates it from its existing still-assigned-to-this-worker computation; Asana populates it from `task["completed"] == false`, independent of section/state, closing the real completed-vs-section-name gap (FR-017); Bindle and every other adapter leave it at its safe default.
- **Bindle Task-Completion Agent Tool** (restored, this feature, corrected 2026-08-27 — see Correction Note): the narrow, agent-invoked, session-scoped tool FR-025/FR-026 define, exposed through `agent_tool_specs/0`/`execute_agent_tool/3`. Marks only the one Bindle task bound to the requesting session `done`, via `bindle work done <id>` followed by a best-effort `bindle work publish` (FR-027). Infers nothing from mechanical evidence; fires only on the agent's own explicit request. Exposes no milestone review/acceptance path.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can configure `tracker.kind: bindle` against a real Bindle repository and have Symphony successfully poll, dispatch, and run a coding-agent session against a dispatchable Bindle task through the unmodified orchestrator/agent-runner path.
- **SC-002**: In a test seeding two concurrent acquisition attempts against the same Bindle task, exactly one succeeds and the other is treated as unavailable — never both, never neither, never a crash.
- **SC-003**: In a test driving a running or blocked issue's projection to `dispatchable: false` with unchanged active state and unchanged routing, the running agent is not terminated and the held block is not released — verified directly against `Orchestrator.reconcile_issue_state/4`, `Orchestrator.reconcile_blocked_issue_state/4`, and `AgentRunner.continue_with_issue?/2`.
- **SC-004**: Every existing adapter's own test suite (dispatch, release, continuation, including Linear's assignee-reassignment stop and Asana's completed-vs-section-name handling) passes unmodified in outcome after this feature's changes.
- **SC-005** (corrected 2026-08-27 — see Correction Note): No test, code path, or module in this feature reads or interprets a Bindle dependency/blocking, milestone, or evidence table/column, or calls any Bindle write operation other than `bindle work claim`/`release`/`done`/`publish`; the orchestrator-owned claim/release seam (FR-005–FR-009) never invokes `done` or `publish`; the only code path that ever invokes `done`/`publish` is the one narrow, agent-invoked, session-scoped task-completion tool (FR-025–FR-027), which cannot target any Bindle task other than the one bound to the requesting session and exposes no milestone review/acceptance path.
- **SC-006**: In a test simulating acquisition succeeding immediately followed by a worker-spawn failure, exactly one compensating release call fires before the ordinary spawn-failure retry is scheduled, and that retry's own subsequent acquisition attempt succeeds rather than being rejected as already-claimed.
- **SC-007**: In a test simulating a crash between a successful acquisition and the corresponding work being fully underway, this deployment's startup-time reconciliation — enumerating the current projection and issuing owner-scoped releases, with bounded follow-up retries for any individual release failure (FR-029) — recovers the stale claim without requiring a full process restart and without requiring Symphony to have separately recorded that it previously claimed that specific task; if the bounded retry budget is exhausted, the test confirms a persistent, operator-visible failure is logged rather than the claim being silently declared recovered.
- **SC-008**: In a test driving an issue through a crash-mid-run retry (the issue already present in `state.claimed` because its worker actually started), the retry's re-validation does not require `dispatchable = true` and `acquire_issue/2` is not called a second time for that issue — verified directly against `retry_candidate_issue?/2`'s continuation-mode behavior and `spawn_issue_on_worker_host/5`'s fresh-admission-only acquisition gating (FR-016/FR-024); the retry succeeds using the already-held Bindle claim rather than being rejected as already-claimed.
- **SC-009**: In a test where an agent's coding session invokes the task-completion tool for its own bound Bindle task, `bindle work done <id>` is called for exactly that task's id (never a model-supplied id for a different task), followed by a best-effort `bindle work publish`; a simulated `publish` failure after a successful `done` is surfaced as a distinct failure and does not trigger a second `done` call.
- **SC-010**: In a test simulating a task previously running under Asana whose `completed` flag flips to `true` while its section/state remains unchanged, continuation stops (via `continuation_allowed`) even though label match and `state` alone would not have caught it — confirming the previously-open `completed`-vs-section-name gap (`002-bindle-integration` research.md R11) is actually closed, not merely documented.

## Out of Scope / Non-Goals

- Bindle's own internal schema, storage engine, dependency/claims/evidence model, reconciliation logic, or the mechanics of publishing the projection artifact — entirely Bindle's own project (per `002-bindle-integration`).
- Mechanical evidence verification of any kind — remains entirely inside Bindle (`002-bindle-integration` FR-012, Non-Goals).
- Automated inference of semantic correctness, completeness, or milestone acceptance from mechanical evidence — remains human-resolved by design (`002-bindle-integration` FR-013 as corrected). Milestone review/acceptance of any kind is out of scope for this feature and has no code path anywhere in this design (FR-019/FR-023). This does **not** exclude the one narrow, agent-invoked, session-scoped task-`done` tool FR-025–FR-027 restore, per `002-bindle-integration` FR-013's corrected task-done/milestone-accepted distinction (research.md R16 there) — that capability is in scope, not out of it, as of this correction pass; see this spec's Correction Note.
- `bindle symphony init/start/status` or any other convenience/UX wrapper tooling around this integration.
- Any migration or synchronization mechanism between Symphony's standalone local tracker and the Bindle-backed tracker — the two remain fully independent, non-interacting stores (`002-bindle-integration` User Story 4).
- Multi-instance Symphony deployment support beyond what Bindle's own claim arbitration already guarantees for concurrent acquisition attempts — this feature relies on that guarantee but does not build new multi-instance orchestration. This feature is grounded on a single-active-process-per-owner-identity model: exactly one Symphony process is expected to be actively using one persisted owner identity against one Bindle repository at a time; coordinating multiple simultaneously-running Symphony processes sharing one owner identity is out of scope.
- Reopening or rewriting `001-local-tracker-multi-agent` or `002-bindle-integration`'s frozen specifications.

## Assumptions

- `002-bindle-integration`'s frozen contract (FR-001–FR-017, its Key Entities, and its Assumptions, including FR-013 as corrected 2026-08-27) is authoritative for this feature's architectural boundary; this feature implements it rather than re-deriving it, correcting only where re-verification against Bindle's and Symphony's actual current code finds the prior contract's grounding stale.
- Bindle's published projection schema (`task_projection` table: `id`, `identifier`, `title` (nullable), `description`, `status`, `dispatchable`, `created_at`; `PRAGMA user_version = 1`) and its `bindle work claim/release/done/publish` CLI contract (exit-code/stderr convention, `cwd`-scoped ledger resolution, no `--repo` flag, no JSON output, `--worktree`/`--branch` both optional on `claim`, no `--owner` argument on `done`/`publish`, no `--publish` flag or auto-publish hook on any lifecycle-mutating command) are as directly verified against Bindle's actual current implementation (`~/Developer/bindle`, `src/bindle/work_ledger.py`, `src/bindle/symphony_projection.py`, `src/bindle/cli.py`, `contracts/task-write-surface.md`, `specs/002-milestone-task-work-items/spec.md`, `docs/DECISIONS.md` D038) during this feature's grounding and correction passes; a future incompatible Bindle-side schema or CLI change is handled by this feature's fail-loud version check (FR-002), not by this feature anticipating it further.
- The retry/claim race this correction pass fixes (FR-016/FR-024) was verified directly against `orchestrator.ex`'s actual control flow, not assumed: `refresh_issue_for_dispatch/1` (and the `retry_candidate_issue?/2` re-validation it calls via `revalidate_issue_for_dispatch/3`) is the exact same function shared by both the fresh-dispatch path (`dispatch_issue/4`) and the retry-continuation path (`handle_active_retry/4`), which both ultimately converge on the same `spawn_issue_on_worker_host/5` acquisition call site; nothing in today's code (before this feature) distinguishes the two modes, because no adapter today has a durable claim for either mode to conflict over.
- `continuation_allowed` (FR-013/FR-017) replaces the first correction pass's `routed_by_assignment` naming: verified directly against `asana/client.ex` that `state` (from `memberships.section.name`) and `dispatchable` (from `task["completed"]`/`resource_subtype`) are independently-set fields with no code tying them together, confirming Asana's `completed`-vs-section-name gap is real, not merely possible, and that a Linear-specific field name/semantics ("still assigned") would not have generalized to Asana's actual (state-shaped, not assignment-shaped) continuation-revoking signal.
- The restored task-completion tool (FR-025–FR-027) and its `bindle work publish` follow-up were designed against Bindle's actual write surface, not invented: `bindle work done <id>` takes no `--owner` argument and categorically rejects a milestone id (`not_a_task`); `bindle work publish` is a fully separate, manually-triggered command with no flag or hook on `done` (or `claim`/`release`) that would trigger it automatically — confirmed by direct inspection of `src/bindle/cli.py`'s subcommand wiring finding no cross-call between them.
- The startup-reconciliation bounded-retry fix (FR-029) reuses the orchestrator's existing `schedule_issue_retry/4` timer/backoff primitive rather than introducing a new scheduling mechanism, consistent with this feature's existing decision (data-model.md §6) not to add a local claims ledger — the fix only ensures an individual release failure within the sweep gets bounded follow-up attempts instead of requiring a full process restart to retry at all.
- `exqlite` is already a Symphony dependency (`mix.lock`, `~> 0.30`, currently resolving `0.40.0`); this feature reuses it rather than adding a new SQLite library, unless implementation-stage investigation finds it unsuitable for read-only-mode access, in which case that finding is documented at the planning stage.
- A stable owner-identity string and a startup-time, projection-enumeration-based release pass are new Symphony-side state and behavior this feature must design and build; `002-bindle-integration` explicitly left both as open design questions for this feature's planning stage, not as already-solved edge cases. This feature deliberately does not add a local record of which tasks this deployment previously claimed — Bindle's own safe-release guarantee (a release for a task not held by this owner is a no-op) makes such a record unnecessary, and a local record that could itself go stale or fail to be written before a crash would not actually make recovery safer.
- `repo_path` (the Bindle repository root the CLI is invoked against) is expected to default to `Config.workflow_dir()` — the directory containing the active `WORKFLOW.md`, which is itself copied into the same repository Symphony coordinates work in — since a Bindle-backed deployment's target repository and Symphony's own workflow repository are the same repository in the common case; an explicit override remains supported for a deployment where they genuinely differ. The projection artifact's default path is resolved relative to `repo_path`, not relative to `Config.workflow_dir()` independently, so the read side and write side cannot accidentally target different repositories by default.
- The concrete config field names for `tracker.kind: bindle`'s provider settings (projection path override, Bindle repository path, CLI binary name/path, owner-identity storage location) are an implementation decision for this feature's planning stage, following the existing per-adapter `tracker.provider` convention.
- This feature's admission/continuation fix (FR-013–FR-017) is a generic correction to Symphony's own reconciliation semantics, required for every tracker, not a Bindle-specific carve-out — consistent with `002-bindle-integration` FR-017's own framing.
