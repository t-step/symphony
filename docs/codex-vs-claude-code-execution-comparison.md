## 2. Executive comparison

Claude Code fit into Symphony's existing provider boundary cleanly at the *dispatch* layer: the `CodingAgent` three-callback behaviour — extracted from Codex's pre-existing shape — absorbs both providers with essentially zero branching in `AgentRunner`, `Orchestrator`, `AgentRuntimeSupervisor`, or `Workspace`. Below that seam, the two implementations are genuinely different pieces of machinery, because the providers themselves are different kinds of things: Codex is a long-lived JSON-RPC app-server process Symphony drives as a client; Claude Code is a stateless CLI Symphony re-invokes per turn, for which Symphony had to become an MCP *server* just to expose tracker tools back to it. The Claude path isn't simply simpler or more complex — it trades Codex's protocol-parsing complexity for process-supervision and its own HTTP-server complexity. The most interesting result is how little of the divergence was accidental: nearly every major difference (MCP-hosting inversion, session-identity ownership, allow-list vs. deny-list credentials) is explicitly named and dated in `research.md`'s addenda, meaning the design was actively corrected mid-flight rather than converging by luck — and the final code ended up *more* symmetric with Codex than the original plan expected.

## 4. Where they stayed symmetric

- **The `CodingAgent` 3-callback contract** (`start_session/2`, `run_turn/4`, `stop_session/1`) — a real behaviour, not a shared call signature wrapping incompatible internals. `session` is deliberately opaque (`term()`), so each provider hides arbitrary state behind it. `AgentRunner`'s turn loop, retry logic, and continuation needed zero provider branching to support Claude.
- **Session identity fixed once at session start** — not originally symmetric in the plan (a "prior gap" per `research.md` R7); deliberately corrected until Claude matched Codex's existing behavior, not the reverse.
- **Workspace-cwd validation logic** — near-identical containment checks in both `AppServer` modules, explicitly mirrored per `research.md` R5. Workspace *creation* and lifecycle hooks (`before_run`/`after_run`) live one layer above the provider seam, in `agent_runner.ex` + `Workspace`, and are fully shared.
- **`PathSafety`, `PromptBuilder`, `Local.Adapter`'s tool-spec/execute surface** — fully provider-agnostic; the `Tracker` behaviour that backs the local-issue-tracker tools doesn't know which coding agent is calling it.
- **Cancellation at the orchestrator level** — `Task.Supervisor.terminate_child/2` is identical and provider-blind.
- **The downstream event-atom vocabulary** (`:session_started`, `:turn_completed`, `:turn_failed`, …) and the `Orchestrator.handle_info` clause that consumes it — provider-blind, pattern-matching only on `%{event:, timestamp:}`.
- **Credential-isolation *policy* (FR-009)**, even though the *mechanism* differed and was briefly asymmetric (§5) — both integrations now actively strip the other provider's credential.

## 5. Where they diverged

- **Process model is inherent, not chosen.** Codex's app-server is long-lived because that's what the `codex app-server` binary is; Claude's per-turn process is forced by headless mode having no persistent server. This cascades into MCP hosting, session-identity ownership, and cancellation shape.
- **MCP hosting direction is inverted — the largest genuine architectural divergence, and it was *discovered*, not planned.** `research.md` (R6) records that the original plan assumed Claude would spawn its own MCP child process the way Codex's tool calls "obviously" generalize. That assumption doesn't compose — a child of `claude` isn't a child of the BEAM. The corrected design makes Symphony the MCP *server* for Claude while staying the MCP *client* for Codex: a real role inversion, not just a wire-format difference.
- **Permission model is protocol-shaped vs. flag-shaped**, and there's no way to make these more symmetric — it's a hard consequence of one provider having an interactive approval protocol and the other not.
- **Credential-isolation mechanism differs by necessity of the launch strategy.** Codex goes through `bash -lc`, so isolation is a deny-list (`unset ...` + `env:` deletions); Claude is a direct `:spawn_executable` with no shell, so isolation is an allow-list. Both now achieve the same FR-009 goal, via mechanisms forced by how each provider is launched — but see the historical note below: this was **not always symmetric**. `ANTHROPIC_API_KEY` leaked into Codex subprocesses (both local and SSH) from commit `918f845` through `632f787`/`a540239`, closed only in the HEAD commit `099535b`. The allow-list model was safe by construction from day one; the deny-list model required someone to remember to enumerate the foreign credential by hand, and initially didn't.
- **Worker-host support is Codex-only, and not by oversight** — `ClaudeCode.AppServer` actively rejects a `worker_host` argument, reinforced at config-validation time. A documented release-scope boundary.
- **Auth strategy moved *away* from strict isolation over time** — Claude's default was originally `--bare` (forces `ANTHROPIC_API_KEY`-only, tightest isolation), then switched via commit `a540239` to `--setting-sources project,local` (uses the operator's existing OAuth/subscription login, loads repo-scoped `CLAUDE.md`/hooks/settings). This pulls in the opposite direction from the credential-hardening happening on the Codex side in parallel — both correct and deliberate, but the two integrations don't share one philosophy on isolation-vs-usability.
- **Explicit OS-process kill exists only on the Claude path**, with Codex's `stop_port/1` doing only `Port.close/1`.

## 6. Lifecycle comparison — one work item, dispatch → cleanup

**Dispatch (identical):** `Orchestrator` claims an issue, spawns `AgentRunner.run/3` under a `Task.Supervisor`, and monitors the pid. `AgentRunner` creates the workspace, runs the `before_run` hook, then calls `CodingAgent.resolve/0` — the *only* branch point in the whole path, mapping `agent_execution.kind` to a module.

**Startup:**
- *Codex* — `start_session/2` opens `bash -lc "unset <secrets> && exec codex app-server"` via `Port.open`, sends `initialize`/`initialized`, then `thread/start`, capturing a `thread_id`. One process, will live for the whole run.
- *Claude* — `start_session/2` generates a UUID `session_id`, starts a `ClaudeCode.MCPServer` Bandit listener on `127.0.0.1:0` with a per-run bearer token, writes a temp `--mcp-config` file pointing `claude` at that listener, and checks once for a repo-owned `.mcp.json`. No OS process yet.

**Execution, per turn:**
- *Codex* — sends `turn/start` over the already-open Port; the receive loop dispatches `item/tool/call` directly to `Codex.DynamicTool.execute/4` in-process; approval-request RPCs are intercepted and auto-approved or fail the turn per policy.
- *Claude* — spawns a **fresh** `claude -p "<prompt>" --session-id|--resume <uuid> --output-format stream-json ...` process; the receive loop tracks a `:bootstrap → :turn` phase gated on seeing `{"type":"system","subtype":"init"}`. Tool calls never touch this Port — `claude` reaches out over loopback HTTP to `ClaudeCode.MCPServer`, which calls `Tracker.execute_bound_agent_tool/4` directly.

**Events/results:** both funnel through `emit_message` into the same `%{event:, timestamp:, ...}` envelope, forwarded by `agent_runner.ex` as `{:codex_worker_update, issue_id, message}` regardless of provider — `Orchestrator.handle_info` is identical either way.

**Cleanup/cancellation:**
- *Normal completion* — Codex: `Port.close/1`. Claude: stop the MCP listener, delete the temp `--mcp-config` file, and `close_port/1` (which `kill -9`s the OS pid first).
- *Orchestrator-forced cancel* — `Task.Supervisor.terminate_child/2` kills the `AgentRunner.run/3` task for both. Neither `AgentRunner` nor the spawned `Task` traps exits, so under ordinary OTP semantics a forced kill likely skips the `after`-block cleanup (`coding_agent.stop_session/1`) for **both** providers — a shared, unconfirmed risk, not a provider divergence (see §9).

## 7. What surprised you

- **How little of the divergence was left to chance.** Nearly every major difference — MCP-hosting inversion, session-identity ownership, allow-list vs. deny-list credentials, shell-vs-argv command parsing — is explicitly named, justified, and dated in `research.md`'s addenda. Someone reading only `plan.md`/`data-model.md` would expect Claude's tool exposure to mirror Codex's in-process dispatch; that assumption was caught and reversed before it shipped, not after.
- **The credential-isolation gap was a real, live leak for four commits, not a design uncertainty** — `ANTHROPIC_API_KEY` genuinely reached Codex subprocesses between `918f845` and `099535b`, caught by a "vend-readiness review," not by the original implementation's own tests.
- **Codex's cleanup path is less defensive than Claude's**, despite being the older, more mature integration — it has no OS-level kill equivalent to Claude's `kill -9`/`Port.close` handling. This inverts the naive expectation that the original path would be the more hardened one; a plausible (not confirmed in-repo) explanation is that a long-lived app-server process reliably exits on stdin/port closure in a way a one-shot CLI subprocess apparently doesn't.
- **A likely real telemetry gap surfaced by static tracing, not by design docs**: `Orchestrator.extract_token_usage/1` and `extract_rate_limits/1` (`orchestrator.ex:1749-1798`) only ever read `update[:payload]`, never `update[:raw]` — but Claude's events carry their payload under `:raw`, and the deep-path probes those functions use (`method: "turn/completed"`, etc.) are shaped for Codex's JSON-RPC envelope, which Claude's flat `stream-json` result never has. Concretely, this suggests `codex_input_tokens`/`codex_output_tokens`/rate-limit fields likely never populate for Claude-backed runs, despite `tasks.md` (T022) explicitly claiming this was wired up, and despite a composition test asserting all-zero token counts as its expected value (which is *consistent* with the gap but not conclusive proof by itself, since that test may simply not exercise a completed turn). **This is a static-trace finding, not dynamically confirmed** — nobody ran a live Claude turn to check the dashboard actually stays at zero.
- **Auth strategy moved away from strict isolation over time** (`--bare` → `--setting-sources project,local`) at the same time credential isolation was being hardened on the Codex side — two deliberate, well-justified decisions that pull toward different values (usability/OAuth-reuse vs. strict cross-provider isolation) rather than one converged philosophy.

## 8. Architectural takeaways

- **The `CodingAgent` boundary is doing exactly what a provider seam should do**: it hides process-model, protocol, and even role-direction (client vs. server) differences from everything above it. `AgentRunner`, `Orchestrator`, `Workspace`, and `PromptBuilder` needed no provider-awareness to support a structurally very different second provider — strong evidence the seam was drawn in the right place, not just that it happened to work this once.
- **What generalized cleanly is narrower than the whole system.** The behaviour contract generalized; the telemetry/config vocabulary (`codex_*` field names, the shared `stall_timeout_ms` knob, and — per §7 — the `:payload`/`:raw` key mismatch) did not, and most of that was consciously accepted rather than fixed, with an explicit note that a third integration would be the trigger to revisit naming. That's a real, bounded leak of provider identity upward, contained to naming and telemetry plumbing, not control flow.
- **Some Codex-shaped abstractions correctly did *not* generalize.** The structured `approval_policy` map and interactive approval protocol are entirely Codex-specific; Claude doesn't reimplement a shadow version of them, it just uses one static flag. The behaviour contract's minimalism (3 callbacks, opaque `session` term) is precisely what made this optional rather than forced — a richer contract exposing approval primitives would have made Claude fake a protocol it doesn't have.
- **Symphony took on a genuinely new responsibility for Claude that Codex never required: being an MCP server.** This is the clearest place the Claude path contains machinery Codex gets for free — Codex's tool exposure is a few lines of in-process dispatch inside an existing receive loop; Claude's is a second HTTP listener with its own auth scheme and JSON-RPC-over-HTTP handling, existing for no other reason.
- **The credential-isolation repair is a concrete data point that supporting two providers surfaces real correctness risk at the seam, not just cosmetic asymmetry.** The two credential-stripping mechanisms differ *because* their launch mechanisms differ — and that structural difference is exactly what let one side's isolation rule silently fail to get ported to the other. General lesson: when two integrations solve the "same" cross-cutting requirement via mechanisms forced by their own protocols, symmetry has to be verified explicitly per requirement; it doesn't fall out of the shared behaviour contract automatically.
- **Final code vs. original design expectation**: the plan initially expected *more* symmetry than the first implementation delivered (the MCP-hosting assumption, the session-identity gap), and the fork got there anyway — through explicit, documented correction, not because the initial design was right the first time.

## 9. Change assessment

**No actual correctness problem and no concerning architectural inconsistency were found at HEAD.** Findings, in order of interest — none warranting action, most already known and dispositioned by the codebase's own authors:

- **Already-fixed correctness problem**: FR-009 credential-isolation asymmetry (Codex not stripping `ANTHROPIC_API_KEY`), live from `918f845` through `a540239`, closed in `099535b` with a regression test documented to fail pre-fix. Historical, not current.
- **One statically-inferred, unconfirmed candidate gap worth a live check**: `extract_token_usage`/`extract_rate_limits` in `orchestrator.ex` appear to never read Claude's `:raw`-keyed event payload, plausibly meaning token/rate-limit telemetry silently stays at zero for Claude-backed runs despite `tasks.md` claiming it's wired up. This is new — not something `research.md`'s addenda call out — and is the one item from this whole investigation worth flagging as genuinely worth a runtime check, hedged as PLAUSIBLE not CONFIRMED since nothing was executed.
- **One observed-but-unconfirmed asymmetry, narrower than a bug**: Codex's `stop_port/1` has no OS-level kill where Claude's `close_port/1` does, with no `research.md` entry or code comment on the Codex side addressing it (unlike every other divergence in this report). Whether this matters depends on `codex` binary behavior outside this repo's visibility, and no test exercises it either way.
- **Expected provider-specific divergence** — the large majority of §5/§3: process model, MCP-hosting direction, permission model, worker-host scope, auth-strategy trade-off. All inherent to the providers or explicit, reasoned fork policy.
- **Known, already-documented, deliberately-deferred gaps**: the shared `codex.stall_timeout_ms` watchdog applying to Claude runs too, and the `codex_*`-prefixed telemetry field names staying unrenamed — both explicitly flagged as accepted debt in `research.md`, not new findings.

Nothing here calls for a code change under the terms this review was scoped to. The one item worth follow-up, if wanted, is confirming live whether Claude-backed runs actually show nonzero token/rate-limit telemetry on the status dashboard — a runtime check this read-only pass could not settle on its own.
